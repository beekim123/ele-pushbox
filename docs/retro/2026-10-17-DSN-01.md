## 5. 犹豫和返工（指出原文）

1. **「场景页能选 theme.jeju」做不到**：DSN-01 验收标准要求这一条；但同一个包的「可改的文件」里没有 `workbench/js/app/views/scenes.js`。两条互相矛盾。我反复确认后，只能把它写成遗留问题。
2. **红蜻蜓 `fed`**：DSN-01 第一步第 3 条要求「worlds.json 的 jeju 补齐 hint_fauna…照 diyu 的写法」；第 5 条又说「不改 content/i18n/*.json」，`content/i18n-rooms2` 也不在可改清单里。可 tests/rooms2.test.mjs 要求 `fed` 和 i18n-rooms2 一字不差。结果是写进去、单测失败、再删掉移交 DLV-04，**返工一次**。
3. **`jeju_1` 放哪**：第一步第 3 条要求「slices.json 加 jeju_1」，又说「不要加进开局池」；但没说清：放进 `entries` 就会报 27 个错，违反验收「0 错误」。我做了副本试验才确定要放顶层 `planned`。
4. **美术版本号**：process.md 第 6 节第 2 条「美术版本只升一次…最后的版本号 = 基线上的版本 + 1」写的是改已有资产的情况；对全新资产怎么算没说。我花时间确认了新资产就是 v1，中间 build 不会把版本号推高。
5. **跷跷板尺寸**：工作包没给尺寸，art-direction 默认 16×16；翘起的端头放不下，改成 16×20，并回头改设计文档和 DLV-05，**返工一次**。
6. **亮天空**：用户要求「明亮」，和 art-direction 第 1 节第 5 条「背景不比地形的中间调亮」冲突；只能自己选方案（待定 1 按 C），再请用户看图定。
7. **item.snack 能不能加动作**：工作包没写；查到已确认资产不能改，只好另做 `item.snack_jeju`。
8. **交付格式**：README 模板的交付只有 5 行要点，WB-01 的实例很长，我照 WB-01 写，篇幅偏长。
9. **工作包太长**：DSN-01 本身约 130 行，加上要读的设计依据，读和反复查花得多；对「可改」和「验收」的交叉核对占了不少时间。

## 6. 交付说明

- 写「交付」一节约占 8%（实际写作本身不长；大部分时间花在为它复核）。
- 为它额外做的事：
  - 读 WB-01 的交付当格式范例；
  - 逐条比对 catalog 改动（catdiff 脚本）、查荞麦凉粉原本是否只属济州；
  - 副本试验重跑一次（为写准 27 个错的分类）；
  - 核对 22 项都是 v1 / review、确认命令里 22 个 id 不重复；
  - 提交前又 build 一次，比对生成文件；
  - 把 diff 统计写进文档，跑 2 轮让它稳定；
  - 打包后在两个临时仓库里试导入。
- 提交次数：共 2 个提交（第 1 个是设计文档，第 2 个包含交付）；没有为交付多提交。

## 7. 重做的话能省什么（从多到少）

1. **画精灵别每改一下就 build**：先用自己的脚本出图看，满意了再一次 build。估计省最多（十几次 build + 看图）。
2. **工作包先把冲突写清**：scenes.js 可不可改、`fed` 归谁、`jeju_1` 放 `planned`、新资产就是 v1、跷跷板尺寸、item.snack 不能加动作。这些都写进包里，就不用试错和返工（省 `fed` 那轮单测重跑、副本试验、尺寸返工）。
3. **全套检查只在最后跑一次**：中间只跑相关的几条（content、rooms2 测试、art build/verify）；单测 + e2e 一轮约 3 分钟，能少跑一轮。
4. **不重复核对**：压缩后的副本试验、catalog 逐条比对、manifest 核对都可以不做，摘要里已有。
5. **交付精简**：照 README 模板 5 条写，不照 WB-01 写长文；diff 统计不写进文档（文档本身会让它变）。
6. **对照图一次定版**：先定好要哪几屏，避免重出。
7. **工作台验证只做验收要求的**：能列出、能播放就够，不逐帧比对。
8. **bundle 只做 verify**，不在两个仓库里试导入。
