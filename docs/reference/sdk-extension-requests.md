## EXT-09 唤醒命令

**效果与最小场景**：提交一条命令，让矩形覆盖的 chunk 中的所有求解器在下一 tick 重新检查这一片，不改动任何 cell 或 layer。

最小场景（复现推箱 D3 的问题）：320×192 的世界，全图基岩。挖出一个 U 形管：左臂 x 144–159、右臂 x 192–207，y 64–143，底部 y 128–143 横向连通。右臂和底部装水到 y 80，左臂 y 112–127 用一格 `crate` 封住，下面 y 128–143 是水。推进到静止后，用 `clear_rect(144, 112, 16, 16)` 清掉封口：

- v1.2.0 的结果（已复现，`_work/measure/wake_test.cpp`）：600 tick 后左臂仍是 0 个水，右臂 y 128 以上仍有 768 个；用降级做法（重写一个水 cell）后两边各 384 个。左臂一直是空的原因：封口在 chunk 行 1，水在 chunk 行 2 和右臂；清除只唤醒了封口所在的 chunk，那里没有水可当种子，`liquid_pressure` 不运行；元胞求解器处理到封口下面的水，但水不能向上走。
- 期望：清除后再提交 `wake_rect(144, 111, 16, 34)`，液压在下一次运行时把右臂的水搬进左臂，两边液面相差 ≤ 1 格。

**为什么现有能力不够**：SDK 的已知现象“休眠的液体看不见远处新开的洞”。只有真正改了 cell 或 layer 才会给 chunk 置上求解器的唤醒位，而液压只在带唤醒位的 chunk 里找种子。现在的降级做法是挑水体中的一个 cell，先写 `empty` 再写回原材料：水量不变，但这个 cell 的随机颜色位和方向位被重新生成，每个邻格多两条命令，而且依赖“写 cell 会唤醒哪些求解器”这一内部细节。推箱 D3 不做这一步就会失败（箱子来回浮沉）。

**期望接口**：

```cpp
// commands.hpp：追加，取下一个可用编号（目前是 18）
enum class CommandType : std::uint8_t { /* …, CreateBodyFromComponent = 17, */ WakeRect = 18 };
// a, b = 左上角；c, d = 宽、高（≥ 1）；material、layer、value 必须为 0；越界部分裁掉，不算错误
```

```gdscript
func wake_rect(x: int, y: int, w: int, h: int) -> int
```

- 执行：对矩形外扩 1 cell 后覆盖的每个 chunk，把相交部分并入 `rect_next`（元胞求解器下一 tick 扫描），并置上全部已登记的求解器唤醒位（`solver_awake |= awake_bits`）。
- 场景文件增加对应的操作，例如 `{"op": "wake", "x": …, "y": …, "w": …, "h": …}`。

**确定性**：只改唤醒位和扫描矩形，没有随机数。唤醒位本来就包含在 `state_hash` 和快照中。

**性能**：与覆盖的 chunk 数成正比，可以忽略。

**存档与回放**：普通命令，进入回放；没有新状态。

**兼容性**：新增命令类型；不提交就没有任何影响。Godot 增加一个方法，升次版本。

**验收**：

- 上面的最小场景：不提交时左臂保持空，提交后 120 tick 内两边液面相差 ≤ 1 格；
- 对完全静止的世界提交后，下一 tick 的 cell 内容不变（只有唤醒位和扫描范围变化）；
- 线程数 1、4、8 下 hash 一致；越界矩形被裁掉，不报错。

## EXT-03 静止查询

**效果与最小场景**：查询“再推进一个 tick，世界中的 cell 会不会变化”，并且可以指定不把某些求解器的活动算进去。用来判断回合制结算何时结束。

最小场景：

1. 倒一格沙到地面上，反复 `step(1)`，直到 `is_settled()` 为真；此后再 `step(10)`，hash 只有 tick 数变化，cell 不变。
2. 世界里有一个 `battery`（period 12）和一段铜线，旁边倒一格沙。`is_settled()` 永远为假（电子一直在动）；`is_settled(["electric"])` 在沙停下后为真。

**为什么现有能力不够**：现在用“连续 N 个 tick `active_chunks == 0` 且 `queue_size == 0`”判断（推箱模板 2.6，N 要大于液压的 `rate_divider`），demo 内容实测可靠。但：

- 有电源的电路：电子移动时 `set_reg` 会唤醒 cell，`active_chunks` 永远不为 0，结算无法结束；
- 有 `thermal` 时：只改温度、不改材料的变化不唤醒 cell，`active_chunks` 为 0 时冰可能还在慢慢升温，之后才融化；
- 判断要逐 tick 读 `get_stats()`，而且依赖各求解器的唤醒细节。

推箱第 8.2 节的电路门、冰桥、引信都会遇到这些问题。

**期望接口**：

```cpp
bool World::is_settled(std::span<const std::string_view> ignore = {}) const;
// 命令队列为空，且除 ignore 列出的求解器外，每个求解器都报告空闲
// Solver 新增 virtual bool idle() const，默认“没有带本求解器唤醒位的 chunk，也没有排队的工作”；
// liquid_pressure：上次运行没有搬动任何 cell；thermal：上次运行没有任何格的温度跨过相变或着火阈值，且温度变化都小于某个阈值（由维护者定义）
```

```gdscript
func is_settled(ignore: PackedStringArray = PackedStringArray()) -> bool
```

**确定性**：只读，不影响模拟。

**性能**：O(求解器数)。

**存档与回放**：不涉及。

**兼容性**：新增虚函数，带默认实现；升次版本。

**验收**：

- 沙堆、U 形管、慢速液体三个场景中，`is_settled()` 第一次为真之后，再推进 60 tick，除 tick 数外状态不变；在为真之前，至少有一个 tick 的 cell 发生了变化；
- 上面的电路场景按描述成立。

## EXT-06 液体流量读数

**效果与最小场景**：登记一条水平或竖直线段，SDK 累计每 tick 净穿过它的液体 cell 数（正方向减反方向）。

最小场景：竖井中放 1024 个水 cell，下落时穿过一条水平线段，读到的累计值为 1024。

**为什么现有能力不够**：塔防 v0.3 的水车把落进接水槽的水数完就清掉（塔防模板 3.5），水到此为止。以后如果要让水“流过水车后继续往下流”（比如水车下游还有水塘），就只能靠区域存量的差去推算，分不清“经过”和“停留”的水。

**期望接口**（由维护者决定放在哪里）：

- 方案一：元胞求解器的可选参数，交换 cell 时检查是否跨过登记的线段；
- 方案二：新的可选求解器 `flow_gauges`，线段写在 profile 的新顶层字段 `flow_gauges` 中（下面只列 profile 里新增的部分）：

```json
{"flow_gauges": [{"id": "w1", "x": 16, "y": 128, "len": 64, "axis": "h"}]}
```

```cpp
Result<std::int64_t> gauge_total(const World&, std::string_view id);
```

```gdscript
func gauge_total(id: StringName) -> int
```

**确定性**：计数只依赖 cell 的移动，在固定阶段汇总，与线程数无关。

**性能**：每条线段每 tick 小于 1 µs（与穿过量成正比）。

**存档与回放**：累计值要进快照。

**兼容性**：可选；不声明线段就没有任何影响，内容 hash 不变。

**验收**：

- 上面的场景通过；
- 来回晃动的水，净值为 0；
- 液压搬运跨过线段的 cell 也被计入；
- 线程数 1、4、8 下结果一致。

## EXT-10 渲染瓦片边缘

**效果与最小场景**：自定义着色器（`render_shader_path`）能读到当前像素上下左右至少 2 格的材料，即使那些格在隔壁瓦片里。最小场景：一条横跨 x = 256 的水面，着色器给“上方是空”的水 cell 画高光，接缝两边的高光连续。

**为什么现有能力不够**：Godot 适配层把世界切成 256×256 的瓦片，每个瓦片一张 256×256 的纹理、一个 Sprite2D，着色器只能 `texelFetch` 本瓦片的纹理。挖痕暗边、受光边、水面高光都要看邻格，接缝处读不到，会断一像素。

**期望接口**（由维护者决定）：

- 方案一：瓦片纹理改为 (256 + 2a)×(256 + 2a)，四周带 a 格（默认 2）的边缘，`encode_chunk` 同时写入邻近 chunk 的数据；着色器通过 uniform `apron` 知道偏移；
- 方案二：提供一张整个世界的材料纹理（`get_world_texture()`，按 chunk 版本增量更新），游戏可以用自己的 Sprite 和着色器画。

**确定性**：只影响渲染，不影响模拟和 hash。

**性能**：方案一每瓦片上传量增加约 3%（a = 2）；方案二多一张纹理的增量上传。

**存档与回放**：无关。

**兼容性**：默认 a = 0 时行为与现在完全相同；自带的 `palette.gdshader` 不需要改。

**验收**：上面的场景接缝处高光连续；a = 0 时渲染结果逐像素不变。

## EXT-11 按 tag 过滤的画笔

**效果与最小场景**：`paint_circle`、`paint_rect`、`clear_rect` 增加一个可选的 tag 过滤：只改动“当前材料带有指定 tag”的 cell。最小场景：土（tag `dirt`）和岩（无 `dirt`）各占一半的区域，`clear_rect(…, tag = "dirt")` 之后土全部清空、岩一个不少。

**为什么现有能力不够**：现有画笔模式只能按类别过滤（空、空或流体、非 static）。塔防的土和岩都是 static，模式 3 分不开，所以游戏层要先 `get_material_ids` 读笔刷范围、再按行提交 `clear_rect`。能用，但每个笔刷印要一次读取加十几条命令，而且读和写之间隔了一个 tick 的语义要游戏层自己保证。

**期望接口**：画笔命令的 `mode` 增加一个取值 `PAINT_TAG = 4`，tag 编号放在命令的空闲字段；Godot 侧新增 `paint_circle_tag(x, y, r, material, tag)`、`clear_circle_tag(x, y, r, tag)`。

**确定性**：与现有画笔相同（逐格判断材料，与线程无关）。

**性能**：与同面积的普通画笔相同。

**存档与回放**：命令进回放，格式只追加。

**兼容性**：可选；不用时行为不变。

**验收**：上面的场景通过；同一 tick 内水流进被清掉的格不受影响（命令在求解器之前执行）；回放校验通过。

## 考虑过、暂不提出的需求

这些在 [能力清单](sdk-capability-map.md) 第 4 节列为候选，两份 demo 设计用别的办法绕开了：

| 候选 | 为什么暂不提 |
|---|---|
| 方向性反应（只在“上方”时反应） | demo 没有用到这类规则 |
| 区域事件（材料进出某区域时发信号） | 回合制和每 tick 的计数已经够用 |
| 温度条件反应 | demo 不用温度；冰塔改用耦合器和寿命 |
| 持续风源 | 两款 demo 都没有风 |
| 粒子命中事件 | 塔防的伤害由游戏层直接结算，不用粒子当子弹 |
| 超过 255 tick 的寿命 | 冰用两段寿命（`ice` → `ice_thaw`）拼接；其他计时在游戏层做 |
| 批量读取 layer | demo 只写 layer（`drain`、`frost`），不读 |
