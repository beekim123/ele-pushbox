## B 美术与工作台

| # | 发现 | 类型 | 决定 |
|---|---|---|---|
| B1 | 美术写成 GDScript 字符矩阵、启动时生成纹理（旧 G01）：HTML 与 Godot 各有一套绘制代码，只能靠"逐行一致"的约定来保证相同；也无法对单张图做哈希确认 | 事实 | 美术源数据统一为 JSON（调色板索引像素），导出 PNG 图集与清单，记录 SHA-256；HTML 预览与 Node 导出共用同一份渲染代码；Godot 只加载已确认的 PNG |
| B2 | 旧 Art Lab 页面混合了改稿展示、42 项图鉴、像素编辑、UI 预演和代码复制，入口重复；编辑结果只存在内存中，刷新即丢失；"导出"只是复制片段 | 事实 | 按工作流重建：场景 → 资产 → 编辑对比 → 确认 → 导出；编辑自动暂存在浏览器中，并显示"未导出"状态；导出为可导入仓库的文件 |
| B3 | 没有版本和确认记录，"已验收"是文档里的一句话 | 事实 | 资产有版本号、内容哈希、阶段（草稿 / 待确认）；确认记录单独追加保存，绑定到版本和哈希；修改已确认的资产会生成新版本并回到待确认 |
| B4 | 水与酸主色相同（森林），材料辨识度不足；角色与箱体、目标、危险之间没有视觉层级 | 事实（旧 status 第 20 节） | 建立"玩法信息优先"的配色与造型规则（见 [美术规范](../design/art-direction.md)） |
| B5 | "100% 零损耗 1:1"的承诺没有验证手段 | 事实 | 改为可检验的承诺：PNG 解码后逐像素与源数据一致；代表画面由 HTML 与导出工具各渲染一次，逐像素比对；Godot 截图与参考图的比对方法写入交接说明 |
| B6 | 地形依赖 SDK 瓦片纹理着色，256 格接缝处读不到邻格（EXT-10） | 事实 | 建议游戏层合成：一个着色器同时采样两块瓦片纹理（320 宽的世界只有两块），避免接缝；静态地形纹理用位置哈希，与 HTML 逐像素一致；沙、水用 SDK 随机颜色位，只比对颜色集合 |
