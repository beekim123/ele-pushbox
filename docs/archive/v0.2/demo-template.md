## 1. Demo 范围

一句话：**横版剖面里的推箱解谜。地形是真实的落沙和水，玩家挖沙、倒沙、放水、爆破，改变箱子能去的地方，最后把每个箱子送到目标。**

Demo 要证明三件事：

1. 推箱规则保持离散、可预测，玩家能想清楚再动手；
2. 落沙和水的模拟真的进入推理：沙往哪流、水位涨到哪，决定箱子能不能过去、能不能浮上来；
3. 新内容（材料、机关、关卡）主要靠加数据完成。

| 做 | 不做 |
|---|---|
| 5 个手工房间（D1–D5），每间教一个机制，最后一间综合 | 关卡生成、模型、NPC 对话 |
| 推箱、坠落、登台阶、梯子、挖沙、倒沙、浮箱、炸药、压板、拉杆 | 火、冰、电路、酸（列在第 8 章作为扩充方向） |
| 完整撤销、重开、动作预演、作者解法回放 | 局外成长、货币、商店、徽章 |
| 按局面匹配的提示 | 计时、战斗、角色伤害 |

## 2. 核心循环与核心规则

### 2.1 画面与网格

- SDK 世界 **320×192 cell**，`cell_scale = 2`，画面 640×384 像素（SDK 要求世界宽、高都是 64 的倍数，所以不能用 640×360）。
- 1 **格**（tile）= 16×16 cell = 32×32 像素，全图 20×12 格。坐标 `(x, y)` 以格为单位，原点在左上，y 向下，与 SDK 一致。格 `(x, y)` 覆盖 cell `[16x, 16x+15] × [16y, 16y+15]`。
- 人物、箱子、目标、梯子、压板、拉杆都按格定位。沙和水按 cell 模拟，可以只占一格的一部分。
- 人物不在 SDK 世界里（没有材料），沙和水可以流进人物所在的格；箱子在世界里画成 `crate` 材料，沙和水进不去。

### 2.2 格的分类（离散规则和模拟之间的桥）

世界静止后，游戏层按材料 tag 统计每格的 256 个 cell，把格分成四类（按表中顺序判定）：

| 类别 | 判定（阈值 T 默认 128，可配置） | 人物 | 箱子 |
|---|---|---|---|
| `SOLID` | `#solid` 材料 ≥ T | 不能进入；可以站在上面 | 不能进入；可以压在上面 |
| `SAND` | 不是 SOLID，且 `#loose` 材料 ≥ T | 不能进入；可以站在上面；可以挖 | 同 SOLID |
| `WATER` | 不是前两类，且 `#fluid` 材料 ≥ T | 可以进入，但水不能当地面，人物会沉到底 | 可以进入；木箱可能被托住或浮起（2.4） |
| `OPEN` | 其他 | 可以进入 | 可以进入 |

- 箱子所在的格直接记为 `BOX`，不参与统计。
- **不变式**：static 材料（基岩、裂岩、闸门）在地图里只能整格画；裂岩炸剩不到一半就整格崩落（2.7）；闸门总是整格开关（2.5）。所以任何一格的 `#solid` 要么是 0，要么 ≥ 128，不会出现“岩和沙各半、两类都不够阈值”的格。加新的 static 材料时要保持这一点。
- 下文“能进入”指 OPEN 或 WATER，且格里没有箱子；对箱子而言还要求格里没有人物。

**可读性要求**：画面上要始终能看出每格当前的类别。SAND 和 WATER 格加淡边框，开关在设置里。预演（2.6）显示动作完成后的分类。这样玩家永远不用猜“这一点沙算不算挡路”。

### 2.3 玩家动作

每个合法动作是一个**回合**，可以撤销。不满足条件的动作无效：不算回合，不推进世界，界面提示原因。

| 动作 | 条件 | 效果 |
|---|---|---|
| 走 ← → | 前方格能进入 | 移动一格，然后按 2.4 下落 |
| 推 | 前方格是箱子；箱子另一侧能进入（对箱子而言）；箱子上面没有箱子 | 箱子水平移动一格，人物进入箱子原来的格。没有拉、没有连推 |
| 登台阶 | 走和推都不成立；人物头顶格和前方格的上一格都能进入 | 人物斜向上移动一格。只能登一格高；箱子不能登 |
| 爬梯 ↑ | 当前格是梯子，上一格能进入 | 上移一格 |
| 爬梯 ↓ | 下一格是梯子，且能进入 | 下移一格 |
| 挖 ← → ↓ | 目标格是 SAND | 清除目标格中全部 `#loose` cell（水不动），按材料计入**沙袋**；上方的沙随后自然落下 |
| 倒 ← → | 目标格能进入，沙袋不空，目标格里有空 cell | 从目标格最上面一行起，按行优先把空 cell 逐个写成沙，共 n = min(沙袋, 空 cell 数, 256) 个；沙随后自然流动 |
| 炸 ← → ↓ | 炸药预算 > 0 | 在相邻格的中心爆炸（2.7），预算减 1 |
| 互动 | 人物站在拉杆格 | 切换拉杆 |
| 撤销、重开 | 随时 | 撤销回到上一回合开始时，重开回到开局 |

- **← → 的判定顺序**：能走就走；前方是箱子就试推；推不动、或前方是 SOLID/SAND，就试登台阶；都不行则动作无效。所以箱子能推时人物不会登上箱子（D4 用到这一点）。
- 人物不能跳。↑ 只在梯子上有效。
- 沙袋按材料分别计数（demo 里只有沙），**总量守恒**：挖出多少就能倒回多少，只有爆炸会毁掉沙。界面显示为“1.7 袋”（256 cell = 1 袋）。倒的时候按 `rules.json` 中 `pour.order` 的顺序取材料。

### 2.4 坠落、上浮和人物下落（离散结算）

世界静止后，游戏层按下面的顺序结算一**轮**（循环见 2.6）：

1. **崩落**（2.7）。
2. **箱子**：从下到上、从左到右逐个检查。每个箱子一轮只做下面一件事：
   - **坠落**：下一格托不住它时向下移动，直到托得住为止（一轮内可以落多格）。托得住的格：SOLID、SAND、BOX、人物所在的格；对会浮的木箱，还有 `#fluid` cell ≥ `float_support`（默认 64）的格。
   - **上浮**（只对会浮的木箱）：托得住，上一格对箱子能进入，并且箱子接触的水面够高（满足下面任一条），就上移一格（一轮只升一格）：
     - 下一格是 WATER，且与这格 4 连通的 WATER 格（按格算）中，有某格的行号 ≤ 箱子的行号；
     - 左格或右格是 WATER，且与它们 4 连通的 WATER 格中，有某格的行号 ≤ 箱子的行号 − 1。
3. **人物**：所在格变成 SOLID 或 SAND 时（例如沙落进来），上移到同一列上方第一个能进入的格；上方没有能进入的格时，本回合记为“被困”，提示撤销。然后，人物不在梯子格、下一格也不是梯子，且下一格能进入时，向下落，直到落地（一轮内可以落多格）。
4. **机关**（2.5）。

规则说明：

- **为什么托住的门槛（64）低于上浮的门槛（128）**：箱子一浮起，空出的格要分走水，水位随之下降。两个门槛相同时，箱子会在“浮起、落下”之间来回。门槛拉开后，等高的水面不会出现这种来回。
- **为什么只碰到侧面的水要高出一格**：箱子坐在地上、水从侧面涌来时（D3），只有水面高过箱子，抬起箱子后空出的格才会被灌满；水面刚到箱子这一行就抬，空出的格灌不满，箱子又会落回去。
- 结果是**浮着的木箱总停在水面之上一格**，脚下那格至少有 64 个水。
- 箱子每移动一格，在模拟中都是一次**交换**：新位置原有的沙或水被搬到箱子的旧位置，总量不丢（6.3）。同一轮里后处理的箱子要看到先处理的箱子交换后的结果（6.3 的本地副本）。
- **唤醒水体**：箱子离开一格后，如果这格的下、左、右邻格有水，要唤醒那片水（6.3）。SDK 中休眠的水看不到新开的洞，液压不会把水送进去；实测 D3 不唤醒时，箱子浮到 (5,4) 后 (5,5) 一直空着，箱子落回去再浮起来，结算因振荡而停止。

### 2.5 机关

机关全部写在关卡数据里，由**触发条件**和**效果**组成（第 4.4 节）：

- **压板**：格里有箱子或人物时为“通”（可限定只认箱子或只认人物）。
- **拉杆**：人物互动一次就切换一次。
- **水位感应**：指定格是 WATER 时为“通”。
- **材料计数**（通用）：指定矩形内某 tag 的 cell 数 ≥ N 时为“通”。

效果目前只有**闸门**：条件为“通”时打开（闸门格清空），为“断”时关闭（画回闸门材料）。闸门按整组开关：

- 关闭时，组内任何一格里有人物或箱子，或组内的非空 cell 合计超过 `gate.crush_max`（默认 16），就**推迟关闭**，下一轮再判断。
- 不超过时直接关闭，门里那几个 cell 被闸门材料覆盖（消失，不进沙袋，第 9 章 T4 单独计数）。
- 所以一两粒沙或几滴水不会永远卡住闸门；但一堆沙或一池水会把门撑住——这是刻意保留的互动，设计带闸门的关卡时要考虑玩家往门里倒沙。
- 闸门默认两格高，人物不能登过去。

### 2.6 每回合的结算顺序

```
玩家动作（无效动作直接返回）
  → 生成 SDK 命令（推箱 = 交换；挖 = 逐格清除；倒 = 逐格写沙；炸 = explode）
  → 循环（最多 settle.max_rounds 轮，默认 16）：
       逐 tick 推进世界，直到连续 settle.quiet_ticks 个 tick 都满足
           active_chunks == 0 且 queue_size == 0（或推进超过 settle.max_ticks）
       读全图材料 id，重新分类
       崩落 → 箱子坠落和上浮 → 人物脱困和下落 → 机关（2.4、2.5）
       本轮没有任何变化 → 退出循环
       本轮有箱子或人物移动，且移动后的组合（箱子、人物位置和闸门、拉杆状态）
           与本回合开始时或之前某次移动后的组合相同 → 振荡：提交本轮命令后停止，记录关卡错误
       提交本轮生成的命令
  → 判定胜利：每个目标格上都有箱子，且箱子数等于目标数
```

- **静止要逐 tick 判定**。`get_stats()` 只反映最后一个 tick，所以要 `step(1)` 之后检查，不能 `step(N)` 之后再看。液压求解器每 `rate_divider` 个 tick 才跑一次，`quiet_ticks` 必须大于它的 `rate_divider`；本作 profile 把 `rate_divider` 设为 1、`quiet_ticks` 设为 4（4.2）。实测：只看一个 tick 就判静止时，D3、D5 都会在水还没拉平时结算，箱子来回浮沉，关卡失败。
- **停在哪个 tick 必须确定**。画面播放时每帧最多推进 `play_speed` 个 tick（默认 4），但每个 tick 都检查；“跳过动画”只是一帧推进更多 tick，停下的 tick 不变。预演用同一个函数。原因：SDK 的随机数与 tick 有关，同样的命令晚一个 tick 执行，沙堆的形状就会不同。
- 一轮的命令超过 4096 条（SDK 每 tick 的上限）时，分几个 tick 提交，每个 tick 照常检查静止。
- 结算期间不接收输入。
- 16 轮还没结束、某次推进超过 `settle.max_ticks`、或出现振荡，说明关卡设计有问题：记录错误日志，按当前状态继续。只有闸门开关或崩落、没有移动的轮不参与振荡比较（否则崩落后的下一轮会被误判）。第 9 章 T7 保证作者解法不会触发这些情况。
- **开局也先结算一次**再交给玩家：地图上画的沙块如果旁边是空格，会先塌成 45° 的坡（实测 D2 开局就有约 30 个沙塌进人物所在的格）。
- **预演**：玩家选中挖、倒、炸之一和方向、还没确认时，游戏把回合开始时的快照载入一个关闭渲染的预演用 `EleWorld`，用同一套代码跑完本回合，然后用半透明叠加显示箱子、人物的终点和变化了的格子类别。预演不改动真实世界。

### 2.7 炸药

- 调用 `explode(16x + 8, 16y + 8, 20, 8000)`：圆心是目标格 `(x, y)` 的中心 cell，半径 20 cell，power 8000。
- SDK 公式：某 cell 受到的强度 = `power × (r² − d²) / r²`（整数），大于该材料的 `blast_resistance` 时被摧毁。这里等于 `20 × (400 − d²)`：裂岩（300）在 d² ≤ 384 内被毁，沙（200）在 d² ≤ 389 内，水（50）在 d² ≤ 397 内。
- 实测每格被毁的 cell 数（中心格 256 全毁；圆心在格中心偏右下半格，所以右、下比左、上多）：

  | 材料 | 上、左 | 下、右 | 左上 | 右上、左下 | 右下 |
  |---|---|---|---|---|---|
  | 裂岩 | 168 | 184 | 51 | 60 | 70 |
  | 沙 | 171 | 187 | 53 | 63 | 74 |
  | 水 | 173 | 189 | 56 | 66 | 77 |

- **崩落规则**：每轮结算开头，任何含 `#breakable` 材料、且这种材料剩 1–127 个的格，把剩下的全部清掉（逐格 `set_cell`）。所以裂岩要么还在（≥ 128），要么整格消失。对裂岩来说，炸一次正好清掉**十字 5 格**：中心，加上下左右（只剩 72–88 个，崩落）；斜角剩 186–205 个，保留。
- 基岩、箱子、闸门的抗性是 65535，炸不坏。**沙和水会被炸掉**，这是玩家要权衡的代价。
- 爆炸不产生碎片（`max_debris` 为 0），结果可以准确预演。SDK 的爆炸不做遮挡，预演会如实显示墙后的格也受影响。

## 3. 材料与机关

### 3.1 Demo 材料

| 材料 | SDK 类别 | tag | 用途 |
|---|---|---|---|
| `bedrock` 基岩 | static | `solid` `fixed` | 墙和地板，炸不坏 |
| `cracked_rock` 裂岩 | static | `solid` `breakable` | 可以炸掉 |
| `sand` 沙 | powder | `loose` | 可以挖、倒，会流动；在水中下沉 |
| `water` 水 | liquid | `fluid` | 托起木箱，按连通器流动 |
| `crate` 木箱占位 | static | `box` | 箱子在模拟中的身体，炸不坏 |
| `gate` 闸门 | static | `solid` `fixed` `gate` | 机关控制开关 |

梯子、目标、压板、拉杆不是材料，是游戏层画在格上的背景物件，不影响模拟。沙和水可以流过梯子格。

### 3.2 用到的 SDK 能力

| 机制 | SDK 能力 | 说明 |
|---|---|---|
| 沙的流动、堆积、沉入水中 | `cells` 的 powder 和 liquid 移动，按密度置换 | 原样使用。粉末只会直落和斜落，所以沙堆是 45° 坡；液体只在 32 cell 内看到落点时才横流 |
| 连通器（水位拉平） | `liquid_pressure`，`rate_divider` 设 1 | D3、D5 依赖它。被箱子（static）盖住的水面不参与拉平，箱子靠游戏层的上浮规则抬起 |
| 炸药 | `explosions`、`blast_resistance` | 不需要 `thermal` 和 `particles` |
| 挖、倒 | 逐格 `set_cell`（每格最多 256 条命令） | 现有画笔只能按类别过滤（空、流体、非固体），不能只清沙不清水，也不能限量 |
| 闸门开关 | `paint_rect` 和 `clear_rect` | 原样使用 |
| 分类 | `get_material_ids(0, 0, 320, 192)` 一次读全图（61440 格，未超过 65536 的上限） | 游戏层按材料 tag 计数；可以用 `get_chunk_version` 只重算变了的 chunk |
| 静止判定 | `get_stats()` 的 `active_chunks`、`queue_size`，逐 tick | 2.6；扩充内容里有电路或温度时不够用，见 EXT-03 |
| 唤醒休眠的水 | 对水体中一个 cell 先写 `empty` 再写回原材料 | 6.3；有了 EXT-09 后换成一条命令 |
| 撤销、预演 | `save_snapshot`、`load_snapshot`；预演用第二个 `EleWorld` | 快照写文件，实测每个约 213 KB |
| 回归测试 | `get_state_hash` | hash 含 tick 数，只用于“同一动作序列”的比较；提示匹配用局面键（7.3） |

### 3.3 新机制一览

| 编号 | 机制 | 一句话 | 由谁实现 |
|---|---|---|---|
| M1 | 推箱与坠落 | 箱子水平推一格，悬空就落 | 游戏层 |
| M2 | 登台阶 | 人物能登一格高，沙堆和箱子都能当台阶 | 游戏层 |
| M3 | 挖与倒 | 沙进沙袋、倒出来会流，总量守恒 | 游戏层发命令，SDK 模拟 |
| M4 | 浮箱 | 木箱停在水面上一格；水位由连通器决定 | 游戏层结算，SDK 模拟水 |
| M5 | 沙入水抬水位 | 沙沉到水底、把水挤高，从而抬起木箱 | 完全由 SDK 涌现 |
| M6 | 炸药 | 毁沙毁水，裂岩十字崩落 | SDK 爆炸，游戏层做崩落规则 |
| M7 | 机关 | 压板、拉杆、水位、材料计数 → 闸门 | 游戏层读世界，用命令开关 |

## 4. 数据模板

目录约定（Godot 工程内）：

```
res://pushbox/
  content/default/materials.json   # ele.materials/1
  content/default/profile.json     # ele.profile/1
  content/default/reactions.json   # ele.reactions/1（demo 为空表）
  rules.json                       # pushbox.rules/1：分类、动作、炸药、结算参数
  levels/d1.json … d5.json         # pushbox.level/1
```

4.1、4.2 的 JSON 已用 SDK 1.2.0 的解析器加载并建出 320×192 的世界，没有诊断信息。空的反应表写成 `{"format": "ele.reactions/1", "reactions": []}`。

### 4.1 材料 `content/default/materials.json`

```json
{
  "format": "ele.materials/1",
  "materials": [
    {"name": "empty", "class": "empty"},
    {"name": "bedrock", "class": "static", "density": 255, "colors": ["#4A4A55FF", "#44444EFF"],
     "tags": ["solid", "fixed"], "blast_resistance": 65535, "debris_chance": 0},
```

### 4.2 Profile `content/default/profile.json`

```json
{
  "format": "ele.profile/1",
  "name": "pushbox_default",
  "gravity": "down",
  "tick_rate": 60,
  "layers": [],
  "solvers": [
    {"name": "cells"},

```

- `liquid_pressure` 的 `rate_divider` 默认是 4（每 4 tick 跑一次）。设为 1 后每 tick 都跑：实测 D1–D5 作者解法的结算 tick 总数从 1196 降到 730，静止判定也只需连续 4 tick（默认值时要 8 tick）。
- `moves` 是每次运行每片水最多搬几格（范围 1..64）。
- 以后加入火或冰时，再加 `temperature` layer 和 `thermal`（第 8 章）。

### 4.3 规则 `rules.json`

```json
{
  "format": "pushbox.rules/1",
  "tile_cells": 16,
  "classify": {
    "threshold": 128,
    "order": [
      {"class": "SOLID", "tag": "solid"},
      {"class": "SAND",  "tag": "loose"},
      {"class": "WATER", "tag": "fluid"}
    ],
    "box_tag": "box",
    "warn_band": [96, 160]
  },
  "box_kinds": {
    "wood": {"material": "crate", "floats": true, "float_support": 64}
  },
  "player": {"step_up": 1, "dig_dirs": ["L", "R", "D"], "pour_dirs": ["L", "R"], "bomb_dirs": ["L", "R", "D"]},
  "dig": {"tag": "loose"},
  "pour": {"order": ["sand"], "max_cells": 256, "fill": "top_down"},
  "bomb": {"radius_cells": 20, "power": 8000, "crumble_tag": "breakable", "crumble_below": 128},
  "settle": {"quiet_ticks": 4, "max_ticks": 1200, "max_rounds": 16, "play_speed": 4, "wake_water": true},
  "gate": {"crush_max": 16}
}
```

- `classify.order`：按顺序判定，第一个满足“该 tag 的 cell 数 ≥ threshold”的类别生效，都不满足就是 OPEN。加新材料时，只要给它打上 `solid`、`loose` 或 `fluid` 中的一个 tag，分类就自动生效。
- `warn_band`：静止时某格的计数落在 96–160 之间，说明这格的类别“临界”。关卡检查工具会列出来供作者查看；是否真的危险由第 9 章 T3 的阈值扰动测试判断。
- `pour.order`：沙袋里有多种 `#loose` 材料时，倒的顺序；没列出的材料排在后面，按材料名排序。
- `settle.wake_water`：箱子移动后是否唤醒相邻水体（2.4）。关掉只用于测试。
- 关卡可以用 `rules_override` 覆盖其中任何字段（4.4）。

- `budget.sand_cells` 是开局沙袋里的沙（cell）。
- **动作写法**：`L` `R` `U` `D`（走、推、登、爬）、`DIG_L` `DIG_R` `DIG_D`、`POUR_L` `POUR_R`、`BOMB_L` `BOMB_R` `BOMB_D`、`USE`。

- 机关条件语法：`{"lever": id}`、`{"plate": [x, y], "by": "box|player|any"}`、`{"water": [x, y]}`、`{"count": {"rect": [x, y, w, h], "tag": "loose", "gte": 512}}`（rect 以格为单位），可以用 `{"all": [...]}` 或 `{"any": [...]}` 组合，也可以用 `{"not": ...}` 取反。
- 提示条件语法：`"start"`、`{"box_at": [id, [x, y]]}`、`{"moves_gt": n}`（本关已执行的回合数），以及上面的全部机关条件，同样可以组合。

|---|---|---|
| 1 | 炸 ← | 在 (2,2) 爆炸：裂岩全毁；(1,2) 的沙毁 171 个，(1,1)、(1,3) 各毁 53、63 个。上面的沙落下来、一部分滑进 (2,2)：(1,1) 10、(1,2) 200、(1,3) 256、(2,2) 15 |
| 2 | ← | 人物到 (2,2)（只有 15 个沙，是 OPEN） |
| 3 | 挖 ← | 沙袋 200 |
| 4 | ← | 人物到 (1,2)，站在 (1,3) 的沙上 |
| 5 | 挖 ↓ | 沙袋 456（约 1.8 袋），人物落到 (1,3) |
| 6 | → | 前方 (2,3) 是基岩，登台阶到 (2,2) |
| 7–8 | → → | 人物到 (4,2) |
| 9 | 倒 → | 256 个沙倒进 (5,2)，从开口落进左臂，沉到坑底。挤出的水涨进左臂的 (5,3)，水面达到 A 所在的第 3 行 → A 上浮到 (7,2)。水位拉平后 (5,3)、(7,3) 各 128 个；A 下方 128 ≥ 64，留在 (7,2) |
| 10 | 倒 → | 剩下 200 个沙也倒进左臂，(5,3) 232、(7,3) 224，离托住门槛很远 |
| 11–12 | → → | 人物到 (6,2)，经过 (5,2) 时站在梯子顶端 |

这一关要验证三件事，实测都成立：

- 炸药会毁掉附近的沙：三格 768 个沙炸剩 481 个，挖到手 456 个，仍然够用；
- 沙在水中下沉，把水位抬起来，这完全由 SDK 模拟产生；
- 连通器把木箱抬上来。

更短的解（实测可行，不绕开机制）：只挖 (1,2) 的 200 个沙就倒（10 回合）。A 照样浮起，(7,3) 有 96 个。

倒进左臂的沙量与结果（实测，一次倒完）：少于 128 个时 (5,3) 达不到 WATER，A 不动；128–159 个时 A 能浮起，但 (7,3) 正好 64 个，压在托住门槛上，T3 的阈值扰动会失败；160 个 (7,3) 有 80 个，200 个有 96 个。所以本关要求玩家至少拿到约 160 个沙，作者解法用 456 个。

## 6. 架构

### 6.1 Godot 场景

```
PushboxGame (Node2D, game.gd)        回合控制器：输入 → 动作 → 结算循环 → 胜利判定
├─ World (EleWorld)                  真实世界：auto_step = false，render 开启
├─ PreviewWorld (EleWorld)           预演世界：render 关闭，内容与 World 相同，从快照载入
├─ Board (board.gd，纯逻辑)          格分类、坠落和浮力、机关条件求值、局面键，不直接调用 SDK
├─ Actors (Node2D)                   人物、箱子贴图，跟随格坐标做插值动画
├─ Overlay (Node2D)                  目标、梯子、压板、拉杆、类别边框、预演叠加
└─ UI (CanvasLayer)                  沙袋、炸药、撤销、提示
```

- `Board` 是纯 GDScript 数据类：输入材料 id 数组和规则，输出分类结果和要执行的命令列表。这样可以不开 Godot 窗口做单元测试，以后也能移植到 C++（`_work/measure/pushbox_sim.cpp` 就是一份 C++ 参考实现）。
- 所有改动世界的操作都通过 `World` 的命令方法提交（SDK 游戏侧规则第 1 条）。
- 需要导出回放时才开 `recording`。注意：`load_snapshot`（撤销、重开）会重新开始录制，回放只覆盖最后一次载入之后的部分。回归测试用 `solution_hashes`，不依赖回放。

### 6.2 一回合的调用顺序

```gdscript
func do_action(a) -> void:
    if not board.is_legal(a): return                # 无效动作不算回合
    push_undo()                                     # 存快照和游戏状态
    submit(board.commands_for(a))                   # 命令下一 tick 生效
    for round in rules.settle.max_rounds:
        await settle()
        board.read(world.get_material_ids(0, 0, 320, 192))
        var cmds = board.resolve_round()            # 崩落 → 箱子 → 人物 → 机关；每次移动同步更新本地副本
        if cmds.is_empty(): break
        submit(cmds)                                # 超过 4096 条时分 tick 提交
        if board.oscillating(): log_level_error(); break   # 只比较有移动的轮（2.6）
    check_win()

func settle() -> void:
    var quiet := 0
    var ticks := 0
    while quiet < rules.settle.quiet_ticks and ticks < rules.settle.max_ticks:
        world.step(1)
        ticks += 1
        var s := world.get_stats()
        quiet = quiet + 1 if s.active_chunks == 0 and s.queue_size == 0 else 0
        if animating and ticks % rules.settle.play_speed == 0:
            await get_tree().physics_frame          # 只决定画面节奏，不影响在哪个 tick 停
```

预演世界用同一套代码，`animating` 为 false，在一帧内同步跑完。

### 6.3 箱子的移动（交换）

SDK 没有搬运命令，用现有命令做交换（实测守恒、可行）：

1. 从本地副本取出箱子新位置那 256 个 cell 的材料；
2. 依次提交 `paint_rect(新位置, "crate")`、`clear_rect(旧位置)`；
3. 新位置原来的每个非空 cell，用 `set_cell` 写回旧位置的对应坐标（每格最多 256 条命令）；
4. 更新本地副本：新位置是 `crate`，旧位置是刚写回的内容。同一轮里后面的箱子、人物都按更新后的副本判断；
5. **唤醒水体**（`settle.wake_water`）：旧位置的下、左、右邻格中，每个含 `#fluid` 的格取一个流体 cell（按行优先第一个），提交 `set_cell(x, y, "empty")` 再 `set_cell(x, y, 原材料)`。水量不变，只是让那片水所在的 chunk 醒来，液压和元胞才会把水送进空出的格。有了 EXT-09 后换成一条唤醒命令。

这样沙和水被箱子“挤”到身后，总量不变。多格坠落就是连续几次交换。这个做法会丢掉被搬动 cell 的温度和燃烧状态，demo 没有温度和燃烧，不受影响；加入第 8.2 节的火、冰内容时再评估。

### 6.4 撤销和存档

- 每回合开始前：`save_snapshot("user://undo/<n>.snap")`，同时保存游戏状态 JSON（人物、箱子、拉杆、闸门、沙袋、炸药、回合数）。快照只含世界状态，游戏状态要自己存（SDK 规则第 9 条）。
- 撤销：载入快照 n−1 和对应的游戏状态。实测一个快照约 213 KB；撤销栈保留 200 步约 43 MB。超出后可以从开局重放动作（结果确定，速度较慢）。
- 预演世界直接载入本回合开始时那份快照。

### 6.5 确定性

- 游戏层不使用随机数。遍历顺序固定：箱子从下到上、从左到右，机关按数据中的顺序。
- 静止判定逐 tick 进行，停在哪个 tick 与帧率、动画开关无关（2.6）。
- 同一关卡、同一动作序列 ⇒ 每回合结束时的 `get_state_hash()` 相同，与线程数无关（实测线程 1、8 一致）。回归测试依赖这一点。

## 7. 交互与反馈

### 7.1 操作

| 输入 | 键盘 | 鼠标或触屏 |
|---|---|---|
| 移动、推、登、爬 | 方向键 / WASD | 点击相邻格 |
| 挖 / 倒 / 炸 | 先按 1 / 2 / 3 选择工具，再按方向 | 选择工具后点击相邻格 |
| 确认预演 | 再按一次同一个方向 | 再点击一次 |
| 互动 | E | 点击拉杆 |
| 撤销 / 重开 | Z / R | 按钮 |
| 跳过结算动画 | 空格 | 点击 |

移动类动作直接执行，不需要预演确认。挖、倒、炸先显示预演，再确认一次才执行，因为这些动作改变地形，玩家需要先看清结果。无效动作在人物头上显示原因（例如“这格没有空位可以倒沙”），不消耗回合。

### 7.2 反馈

- 预演叠加：会被摧毁的 cell 闪红；箱子和人物的终点画虚线框；类别会改变的格子画边框。
- 结算动画中，沙和水按 SDK 模拟真实流动；离散移动（箱子浮起、下落）做 6 帧补间。
- 沙袋显示为“1.8 袋”，倒沙时显示本次倒出的量。
- 胜利条件满足后弹出完成面板，在点“下一关”之前还可以撤销。
- 结算触发关卡错误（2.6）时，开发版弹出警告并写日志。

### 7.3 提示

两档：

1. **规则提示**：写在关卡 `hints` 里，按条件触发，例如“木箱会浮在水面上”。
2. **下一步提示**：用**局面键**匹配。局面键 = 人物格、各箱子格（按 id）、拉杆和闸门状态、剩余炸药、全图 20×12 的格类别。当前局面键与作者解法第 k 步结束时的局面键（`solution_keys`）相同，就显示第 k+1 步的动作。不相同时，说明“你已经走上了自己的路线，可以撤销回到提示可用的位置”，并显示最近一个匹配步骤距离现在撤销几步。

不用 `get_state_hash()` 匹配：它包含 tick 数和每个 cell 的随机颜色位，玩家多走一步来回，tick 就不同，hash 永远对不上。

## 8. 扩充指南

### 8.1 只加数据就能做的

下面每项都只改 JSON；前提是代码按第 2、4 章实现（沙袋按材料计数、崩落规则每轮执行、关卡支持 `rules_override`）。

| 想加的内容 | 怎么做 |
|---|---|
| 新关卡 | 新建 `levels/xx.json`，录制作者解法，跑第 9 章的检查 |
| 新沙类（流沙、碎石） | 在材料表加 powder，打 `loose` tag；流沙用 `move_chance` 64 让它流得慢（慢速格会让结算多跑几 tick）。想让玩家先倒出哪种，就写进 `pour.order` |
| 新液体（油：比水轻、浮在水上） | 加 liquid，打 `fluid` tag；密度小于水就自动浮在水面。木箱在油上一样会浮（分类只看 `fluid`） |
| 酸蚀岩 | 新材料 `acid`（liquid，`fluid`），反应表加 `{"a": "acid", "b": "#breakable", "to_a": "keep", "to_b": "empty", "chance": 16}`（酸留下，岩被蚀掉）。被蚀掉一半以上的裂岩格按崩落规则整格消失 |
| 新机关条件 | 用 `count` 条件组合，例如“这个池子里的沙 ≥ 2 袋” |
| 不浮的铁箱 | `box_kinds` 加一项 `{"material": "iron_crate", "floats": false}`，材料表加对应的 static 材料（打 `box` tag、抗性 65535） |
| 新的炸药形状 | 在 `rules.json` 中改 `bomb` 参数，或在关卡的 `rules_override` 里覆盖 |

### 8.2 要加少量代码的

| 内容 | 代码改动 | SDK |
|---|---|---|
| 火与木栅：木栅可以烧掉，水能灭火 | 新工具“火把”：在目标格写高温 | profile 加 `temperature` layer 和 `thermal`；材料表加 `burnable`。燃烧的格会让 chunk 保持清醒，结算会等它烧完；只有温度变化（不变材料）时 `active_chunks` 不计，见 EXT-03 |
| 冰桥：冷冻装置把水面冻成冰，冰是 SOLID；加热装置再化开 | 新机关效果“冻结 / 解冻”：给 `frost` 或 `thaw` layer 画一 tick（与塔防冰塔同一做法） | profile 加两个 u8 layer、`couplers`（`stride` 1）和两条耦合规则：`frost ≥ 1` 时 `#freezable → ice`，`thaw ≥ 1` 时 `ice → water`。冰不带寿命，结算照常静止；不需要 `thermal`。用温度相变也能做，但实测冰在常温下几十秒才化，而且温度变化不算活动，回合结算会提前停，需要 EXT-03 |
| 电路门：电池沿导线送电，电子到达门边时开门 | 新条件 `{"powered": [x, y]}`：结算中每 tick 读该格 `get_cell` 的电状态 | `electric`。有电源时电子一直在动，`active_chunks` 永远不为 0，结算无法静止：需要 EXT-03（不把电路算作活动），或电路关卡改为每回合固定推进 N tick |
| 下沉毒气：人物不能进入 | 新增格类别 `GAS`（tag `gas_block`），人物视为不能进入、箱子可以进入 | `sinks: true` 的 gas 材料 |
| 引信炸药：限时爆炸 | 需要先有火把（上面第一行）；崩落规则会自动处理爆炸结果 | `explosive` + `burnable`，需要 `thermal`；`burn_time` ≤ 255 tick，结算会等到它爆炸 |

### 8.3 加新机制的检查清单

1. 先查 [能力清单](../../reference/sdk-capability-map.md)，能用内容或 profile 表达的，不写代码。
2. 新规则只能放在“结算循环”的某一步里，并且是确定的：没有随机数，遍历顺序固定。
3. 新的格类别要在 `rules.json` 的 `classify.order` 中登记，并给出画面上的识别方式。
4. 会持续变化的 SDK 机制（电路、温度、长寿命材料）要先确认结算还能静止（2.6）。
5. 写一个教学房间和作者解法，跑通第 9 章的全部检查。
6. 需要 SDK 新能力时，写进 [../shared/sdk-extension-requests.md](../../reference/sdk-extension-requests.md)，同时写出现在的降级做法。

## 11. 设计决定记录

| 决定 | 理由 |
|---|---|
| 推箱规则保持离散：按格移动，不能拉，不能连推；沙和水由 SDK 连续模拟，两者靠格分类（2.2）衔接 | 玩家能想清楚再动手，同时模拟真的进入推理 |
| 箱子可以坠落，木箱会浮；箱子不会被毁，也炸不坏 | 侧视下最直观的物理；箱子必须送达，不能当材料 |
| 上浮比托住难（128 对 64）；只碰到侧面的水时要高出一格才浮 | 防止浮起、落下来回振荡；实测 D3、D5 在阈值 ±24 下结果不变 |
| 箱子离开后唤醒相邻水体 | SDK 的休眠水看不到新开的洞；不唤醒时 D3 失败 |
| 静止判定逐 tick、连续 4 tick；液压每 tick 运行 | 只看一个 tick 会在液压两次运行之间提前结束（D3、D5 实测失败）；逐 tick 判定保证预演和真实世界停在同一个 tick |
| 人物能登一格台阶，不能跳；← → 先推后登 | 沙堆和箱子都能当台阶；不考验手速；推、登的优先级固定，玩家能预期 |
| 沙挖进沙袋、可以再倒出，总量守恒 | 让“沙流到哪里”成为谜题的一部分 |
| 炸药用 SDK 的 `explode`（半径 20 cell），裂岩剩不到一半就整格崩落；不做遮挡，有预演 | 结果可以预测、可以预演；对裂岩正好是十字 5 格 |
| 闸门 ≤ 16 个 cell 时压掉再关，更多时推迟 | 几粒沙不会永远卡住闸门；成堆的沙、整池的水能撑住闸门，这种互动保留，作为以后关卡可用的解法 |
| 接受更短的解：D5 只挖 200 个沙也能过（10 回合） | 用的仍是本关要教的全部机制；作者解法用 456 个沙，离门槛更远 |
| 画面 640×384（320×192 cell × 2），1 格 = 16×16 cell | SDK 要求世界尺寸是 64 的倍数 |
| 提示两档：规则提示，和按局面键匹配的下一步提示 | state hash 含 tick，不适合匹配；局面键只看玩家能看到的东西 |
| demo 不做局外成长、章节、NPC、关卡生成，不接模型 | 先证明核心乐趣 |
