# 实测结果（2026-10-13 审核轮）

> 历史归档：本文件保留当时的规格、计划或结论，不是当前执行指令。最新目标与新版设计见 [项目文档导航](../../README.md)。目录整理仅修复引用，不重算历史结果。

SDK：ele-base-cpp dacb93e（v1.2.0），本机 Apple clang 17，`build_core.sh` 编译（刚体求解器用桩，demo 不用刚体）。
官方 minimal_cpp 的 state_hash 与 expected.txt 一致（8215ee04e38c4720）。

## 程序

| 文件 | 作用 |
|---|---|
| `build_core.sh` | 把 SDK 核心编进 `build/libele_core.a`，不在 `/tmp/sdkref` 写任何文件 |
| `extract_json.py` | 从模板里抽出 JSON 代码块到 `content/` |
| `load_check.cpp` | 用 SDK 的解析器加载材料、profile、反应并建世界 |
| `bomb_probe.cpp` | 炸药在整块材料上的摧毁格数 |
| `pushbox_sim.cpp` | 推箱回合结算（修订后的第 2 章规则）跑 D1–D5 |
| `snap_size.cpp` | 快照大小、clone 耗时 |
| `cascade_sim.cpp` | 塔防水路：泉池、水车账、中仓放水、敌路水深、淤积、排水、冰塔 |
| `preview_cost.cpp` | 试放水（clone + 900 tick）耗时 |
| `wake_test.cpp` | EXT-09 的最小场景：清掉封口后休眠的水不流进去；重写一个水 cell 后拉平 |

`content/pushbox`、`content/cascade` 是审核前模板抽出的 JSON；`content/final_pushbox`、`content/final_cascade` 是从修订后的最终模板抽出的 JSON（复核用，结果与下文一致）；`content/cascade_v2` 是修订后的塔防内容（冰用耦合器 + 寿命，去掉 thermal）；`content/cascade/map_v2.json` 是修订后的地图。

## 推箱（profile：liquid_pressure rate_divider 1，连续 4 tick 静止）

- 两份原始 JSON 都能被 SDK 加载，没有诊断。
- 炸药 `explode(格中心, 20, 8000)`，整块材料上每格被毁的 cell 数（中心格 256）：

  | | 左上 | 上 | 右上 | 左 | 右 | 左下 | 下 | 右下 |
  |---|---|---|---|---|---|---|---|---|
  | 裂岩 | 51 | 168 | 60 | 168 | 184 | 60 | 184 | 70 |
  | 沙 | 53 | 171 | 63 | 171 | 187 | 63 | 187 | 74 |
  | 水 | 56 | 173 | 66 | 173 | 189 | 66 | 189 | 77 |

  裂岩的上下左右四格只剩 72–88，按“剩不到一半整格崩落”全部消失，所以对裂岩正好是十字 5 格。
- D1–D5 按修订规则全部通关；线程 1、8 的 hash 相同；阈值 104/152、托住门槛 48/80 下结果完全相同（hash 不变）。
- D2：开局 (2,4) 的沙已有约 30 个塌进 (3,4)；挖 ← 得 220；倒 → 后 (4,4)=192（SAND），(3,4)=58（OPEN）。
- D3：拉杆后 A 依次浮到 (5,5)(5,4)(5,3)，共 102 tick；最终 (5,4)=160 水，水箱第 4 行每格 176，第 3 行 0。
  不做“唤醒相邻水体”时，A 浮到 (5,4) 后 (5,5) 一直是空的（水在另一个 chunk 里休眠），A 来回浮沉，关卡失败。
- D4：炸 (9,2) 后整格清空，解法照常。
- D5：炸后 (1,1)=10、(1,2)=200、(1,3)=256、(2,2)=15；挖得 200 + 256 = 456；第一次倒 256 后 A 浮到 (7,2)，(5,3)=128、(7,3)=128；第二次倒 200 后 (5,3)=232、(7,3)=224。
  只挖 (1,2) 的 200 个沙也能过关：倒完后 (7,3)=96，仍高于托住门槛 64（10 步解）。
- 原规则（第一个 `active_chunks == 0` 的 tick 就算静止）：D3、D5 失败。连续 4 tick（rate_divider 1）或 8 tick（rate_divider 4）静止都通过。
- 每回合结算 tick：走一步 4–6；倒沙 35–83；D3 放水 102。
- 快照：320×192 约 213 KB。

## 塔防

- 原始 JSON 能加载。
- 原地图的问题（实测）：
  - 沙脊 (15,9) 开局就向两边塌，各有 36 个沙落进低兜和浅槽；低兜满了以后水越过沙脊流进浅槽：A=1 浅槽约 3、A=2 约 12，和铲开后几乎一样。
  - 泉池 P 出水慢：2 斗在 6.2 s、3 斗在 7.3 s 才流完，原规则的“或 t = 6 s”总是先触发。
  - 用闸门材料直接盖住 GB 会压掉闸门格里 180–200 个水；只往空格画闸门（渐进关闭）2400 tick 也关不上。
  - GW 放完后中仓右端有 16 个 cell 留在地上（离 GW 超过 32 格，液体看不到落点）。
  - D=1 时二号水车实际通过 992–1008 个 cell，按“每满 1024 产 2”会产 0。
  - 冰塔按原参数（降到 1200、冰导热 3）：60 s 内冰不化，反而从 495 格长到 541 格；降到 2150、冰导热 64 也要 37 s。
- 修订内容（`content/cascade_v2`，liquid_pressure rate_divider 1、moves 32；冰用 frost 层脉冲 + 寿命）和修订地图（`map_v2.json`）：
  - GB 在 t = 0 打开，“闸门以外收到的水 ≥ B 斗”时把闸门格的水挪回中仓再关：下路收到 B×1024 + ≤ 15，不损失水；放水全部结束：0/1/1 在 7.4 s，1/2/1 在 8.6 s，0/1/3 在 10.2 s。
  - 水量账逐 cell 对得上（写入 = 现存 + 尾渠吞掉）。
  - 敌路水深（每格 16 列的平均，cell）：

    | | x8–9 路面 | x10–12 低兜 | x13 路面 | x16–25 浅槽 |

  - 冰：一次施放冻住 495 个水 cell，寿命 240–255 + 90–105 tick，5.5–6.0 s 后全部化回水。
  - 淤积（每斗 32 个沙，写在入水口正上方），按 2/0/2、2/1/1、2/2/0（炸岩脊）、2/2/0 四波：上路 x13 的沙 56 → 103 → 147 → 185，那里的水深 13.5 → 10.6 → 7.8 → 5.4；下路 x11 的沙 26 → 79 → 126，水深 17.4 → 12.1 → 9.2。
