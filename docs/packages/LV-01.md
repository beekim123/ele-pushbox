# LV-01 设计模型：机关插件接口 + 关卡检查增强

状态：待审核（基线 `codex/portitor-stage1`，成果在 `claude/lv-01-model`）
设计依据：[关卡质量标准](../design/level-quality.md)；[game-design.md](../design/game-design.md) 第 4 节（格子规则）、6.6；`content/catalog/mechanisms.json` 的 `spec_contract`

## 目标
让设计模型（`workbench/js/core/tilemodel.js`，工作台和 `tools/check-levels.mjs` 共用）能**按机关挂插件**，后面 LV-02–04 各自给第 3、4、5 章的机关写插件、互不冲突；同时让关卡检查直接给出关卡质量标准第 2 节要看的数字。

## 要做的事
1. 插件接口：一个机关一个文件（例如 `workbench/js/core/mech/<机关编号>.js`），向 tilemodel 注册：解析哪些地图字符 / 设备字段、每步结算时做什么、哪些格算支撑或阻挡、怎么参与状态键（搜索去重）。tilemodel 本身只加接口，不改第 1、2 章已有规则的结果。
2. `tools/check-levels.mjs` 每关输出：作者解是否通关、作者解步数、模型最短解步数、"捷径"标记（最短解比作者解短 2 步以上）、死局状态数、搜索是否触顶、有没有用到模型不认识的机关（列出来）。写进 `content/model-check.generated.json`，工作台「模式与关卡」页能看到这些数字。
3. 写一个示例插件证明接口能用：选一个最简单的游戏层机关（建议 `lantern_reveal` 灯照显形或 `nested_box` 套娃箱，按 `mechanisms.json` 的 `spec_contract` 和 game-design.md 的描述），并让对应的 Q08 / Q09 在模型里得到可信结果。
4. 测试：`tests/` 下加插件接口的单元测试（用临时数据）。

### 插件接口（给 LV-02–04）
一个机关一个文件 `workbench/js/core/mech/<机关编号>.js`，以 `PB.tilemodel.register({...})` 注册（照 `lantern_reveal.js` 的外壳写）。`loadMechanisms()` 自动加载该目录所有文件（检查脚本、测试）；**浏览器要在 `workbench/index.html` 的 tilemodel 之后手动加一行 `<script>`**。`tools/art.mjs` 不加载插件（参考图只用 `parse` 取主角位置，保持不变）。字段都可选，只有 `id` 必填：

| 字段 | 作用 |
|---|---|
| `id` | 机制编号；注册后 `unknownMechanisms` 不再报它 |
| `device` | 它管的 `devices[].type`（字符串或数组）；未被任何插件或核心认领的设备类型会被报为"不认识" |
| `chars` | `{字符: CHAR 条目}` 新地图字符；与已有字符冲突会抛错 |
| `init(L, d, k)` | 设备初始 `state.dev[k]`（整数，默认 0） |
| `setup(L, s, d, k)` | 起始状态建好后、第一次结算前（例如把设备绑定到开局的箱子） |
| `settle(L, s, events)` | 每轮结算**最先**调用（早于重力）；改了状态就返回 true，结算会再循环一轮 |
| `solid(L, s, x, y)` | 该格是平台（承重且阻挡），与升降台 / 吊桥同级 |
| `explode(L, s, cells, events)` | `BOMB_*` 清完格子后；`cells` 是爆炸覆盖的 5 格（已去掉出界的） |
| `accepts(L, s, crate, x, y)` | 返回 false 则该箱子不点亮 (x,y) 的槽 |
| `key(L, s)` | 追加到搜索去重键的字符串（`dev`、箱子位置、地形已自动在键里） |

状态约定：能放进 `s.dev[k]`（整数，自动克隆、进键）就放那里；每个箱子的额外状态写在箱子字段上（`clone` 会复制全部字段，但要自己加进 `key()`）；`s` 上新增的顶层字段**不会**被克隆。规格里的 `goals` 可从 `L.goalSpecs` 读。插件之间不应互相依赖执行顺序。核心已认的机制 / 设备清单在 tilemodel 的 `CORE_MECHANISMS` / `CORE_DEVICES`（只有模型真的会模拟的才在里面；fuse、热、气、酸、矿车等都不在）。

### 检查脚本新字段
`node tools/check-levels.mjs [--write] [ID...]` 每关输出并写入 `model-check.generated.json`：`author_ok`、`author_steps`、`shortest`、`shortcut`（作者解 − 最短解 ≥ 2）、`dead_end_states`（搜索不完整时为 null）、`search_capped`（最短解搜索 40 万状态或死局穷举 8 万状态触顶）、`unknown_mechanisms`。原有字段不变。

### 示例插件覆盖了什么
- `lantern_reveal`（Q08）：`cells` 晶桥格；人物与格中心欧氏距离² ≤ 4 才实心；每轮"先更新桥、再重力"，人物落地后再算一次；`dev[k]` 存点亮位掩码。Q08 模型最短解 4 步 = 作者解（插件前是 3 步的假捷径），死局 30 / 45。
- `nested_box`（Q09）：`at` 绑定开局箱子（字段 `nest` 随箱子移动）；每次爆炸最多剥一层，同次多格命中只算一次；只剩一层即普通箱；`goals[].accept.nested_layers` 过滤槽。Q09 最短解 7 步 = 作者解，死局 73 / 117。
- 没覆盖：灯 / 桥的撤销与 SDK 写入 bedrock 单元、"熄灭只清自己的 cell"（SDK 侧）；套娃箱被烧 / 酸蚀剥层（模型无热 / 酸，只处理炸药）；套娃层数在游戏层的撤销保存；`environment` 视觉设置无关性（模型本就不涉及）。这些仍写在各关 `checks` 里，要 SDK / 游戏层核对。
