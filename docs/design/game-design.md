# 游戏设计：规则与关卡模式（唯一有效版本）

版本：GD-4.1（关卡模式 v2），2026-10-15。游戏的整体设定、三个模式和路线图见 [总纲](vision.md)。本文件是三个模式**共用**的格子规则、材料、机关、系统与界面，以及**关卡模式**的完整设计；配送模式、地狱模式、局外养成各有自己的文档。本文件取代仓库此前全部玩法、关卡和阶段规划文档（旧文档保存在快照 `0fae58c`，不再作为执行依据）。修改玩法时只改对应文档，并在文末更新记录中写明。审核过程和取舍理由见 [设计审核记录](../audit/2026-10-15-design-audit.md)；SDK 事实见 [SDK v1.2 核实记录](../reference/sdk-v1.2-verified.md)。

文中三类陈述分开标注：

- **【SDK】** 由 ele-base-cpp v1.2.0（`dacb93e`）的物理求解器完成，已在源码中核实接口存在。具体手感和数值仍需在样板中实测。
- **【游戏层】** 由游戏代码按确定规则执行，例如推箱、压板、门、背包。
- **【待验证】** 设计依据充分，但必须先做样板验证，才能用于正式关卡。

## 1 产品定位

主角是渡界人（PORTITOR）——万界渡口的送货人，什么都送（[总纲](vision.md)）。全程横版、侧视、按格移动的推箱解谜。玩家推箱、攀爬、挖土、倒沙、放炸药；沙、水、气体、火和冰由 SDK 真实模拟。主要乐趣是"我知道这个东西会怎样了，于是可以这样用它"。

**关卡模式**是三个模式的地基：地图都很简单，每关只让玩家发现一件新事；每一章把一种 SDK 材料和几个不需要 SDK 的机关放在一起，章末是把它们合起来用的组合关（第 6 节）。它同时是新机制的试验场和 SDK 的回归测试。以下体验目标和"明确不做"针对关卡模式；配送模式和地狱模式的差异写在各自的文档里。

体验目标：

1. **先看懂，再尝试**。每关开局就能看见目标、可操作物和关键关系，不靠隐藏规则。
2. **试错零成本**。撤销即时可用、无次数限制，重开无确认；失败不扣资源、不计评价。
3. **思考多于执行**。主线没有跳跃、精确时序、长途往返或重复搬运。
4. **物理是因果，不是随机**。动作提交后播放变化，播放结束后再操作；同样的操作永远得到同样的结果。

关卡模式明确不做：俯视章节、跳跃与空中操控、敌人、倒计时、多角色同时操作、星级评分与步数排行榜。怪物、限时货物、步数挑战分别属于配送模式和地狱模式。

## 2 核心循环与操作

循环：观察房间 → 选择一个动作 → 观看结算 → 判断结果 →（撤销或继续）→ 点亮全部目标灯 → 过关。

| 动作 | 键盘 | 鼠标 | 规则摘要 |
|---|---|---|---|
| 走 / 推 / 登阶 | ←→ 或 A D | — | 见 4.2 |
| 爬梯 | ↑↓ 或 W S | — | 只在梯子格内上下 |
| 挖 | 按住 Shift + 方向（左、右、下） | 左键点相邻格 | 挖夯土或散沙，背包 +1 袋 |
| 倒沙 | 按住 Ctrl + 方向（左、右） | 右键点相邻格 | 背包 −1 袋，在目标格生成一格沙 |
| 放炸药（第 3 组起） | B + 方向（左、右、下） | 把炸药图标拖到相邻格 | 见 4.6 |
| 撤销 | Z（可按住连撤） | HUD 撤销按钮 | 无次数上限（存储上限 200 步，超出时丢弃最早的） |
| 重开 | R | HUD 重开按钮 | 无确认，可再撤销回重开前 |
| 观察 | Tab（按住） | HUD 眼睛按钮 | 见 7.4 |
| 提示 | H | HUD 灯泡按钮 | 见 7.2 |
| 暂停菜单 | Esc | — | 继续、提示、重开、选关、设置、返回大厅 |

键盘修饰键方案取代 v0.3 只能用鼠标挖、倒的做法，让纯键盘也能完成全部操作。鼠标点击只对相邻且合法的格生效；悬停时显示目标高亮（7.4）。结算播放中按任意键快进到结算结束，不排队后续输入。

## 3 世界、格子与结算

### 3.1 尺寸

- 逻辑画面 320×180，整数放大（1280×720 为 4 倍，1920×1080 为 6 倍）。非整数倍的窗口留边，不做非整数缩放。
- 1 格 = 16×16 像素 = 16×16 个 SDK cell（`cell_scale = 1`）。
- SDK 世界 320×192（宽和高必须是 64 的倍数【SDK】）。关卡最大 20×10 格，放在 20px 高的 HUD 条下方并居中。
- 关卡房间外圈全是基岩。

### 3.2 两层表示

- **SDK 世界**保存所有材料 cell，负责落沙、流水、反应、燃烧、爆炸等物理。
- **游戏层**保存人物、箱子、背包、门、压板、目标、装置等状态。人物不写进 SDK；箱子同时以 16×16 个 `crate` / `iron_crate` static cell 写进 SDK，让流体和沙能被它挡住。
- **格子分类**：每次结算结束后读取全图材料，按每格 256 个 cell 中占多数（≥128）的类别归类为 SOLID、EARTH、SAND、WATER、EMPTY 等，供移动规则使用（沿用 v0.3 的阈值做法）。

### 3.3 回合结算【SDK + 游戏层】

1. 玩家动作合法 → 保存撤销点 → 游戏层更新实体，并提交对应 SDK 命令。
2. 逐 tick `step(1)` 推进，动画按每帧 4 tick 播放（快进时每帧不限 tick、单帧耗时有预算）。
3. 判定静止：连续 4 tick 满足 `active_chunks == 0`、`queue_size == 0`、`pressure_moves == 0`；启用电路时还要 `electric_heads == 0`。
4. **温度变化不会体现在 Godot 侧的统计里**【SDK，已核实】。凡是依赖温度的装置（点火、加热），都按装置定义的固定阶段长度推进，阶段结束后再判静止。
5. 静止后重新分类格子，游戏层依次执行：箱子与人物的重力、木箱浮起、压板与门；如有变化，回到第 2 步。
6. 单次结算上限 1200 tick 或 16 轮。触顶记为异常：开发版报错，正式版回滚到动作前。关卡设计不得触顶。

### 3.4 搬运不保留状态【SDK，已核实】

推箱、挖土、倒沙、开关门都是"清除旧格 + 写入新格"。新写入的格会重新生成随机颜色位和寿命，燃烧状态清零；温度不会随材料移动，只在新材料定义了 `spawn_temp` 时写入。因此：

- 正在燃烧、带寿命计时、温度异常的材料不能被挖取，也不能被推入或倒入。游戏层先检查这些状态再允许动作。
- 箱子材料不可燃，`blast_resistance = 65535`。

## 4 规则（格子级）

本节规则由 `workbench/js/core/tilemodel.js` 实现为设计模型，供关卡检查与工作台预演使用。模型以整格为单位：第 1 组的规则、第 2 组的水（4.9，整格近似）和机关（4.7、4.10、4.11）都在模型里；气体、火、冰、爆炸的连锁不模拟。模型通过不等于 SDK 验证。

### 4.1 支撑与下落

- 能支撑的格：岩石、裂岩、夯土、沙、关闭的门、箱子。
- 人物所在格的下方不能支撑、自身又不在梯子格内时，人物逐格下落，没有摔落伤害。
- 箱子下方空了就下落；箱子可以叠放，可以压在人物头上（人物离开后再落）。
- 散沙由 SDK 落下和堆积。夯土是 static，挖掉下方的夯土，上方的夯土不会掉落。

### 4.2 水平移动

按优先级依次判断：

1. 前方是箱子，且箱子另一侧可进入：推动箱子一格，人物跟进。每次只推一个箱子，不推箱子链。
2. 前方可进入：走过去，然后执行下落。
3. 前方是能支撑的格，而人物头顶和前方那格的上方都空：**登上一格**。两格高的障碍登不上。
4. 以上都不满足：被挡。播放受阻反馈，不计步数。

"可进入"指空格、水格或背景标记格（梯子、目标槽、压板、出口），且其中没有箱子或人物。

### 4.3 梯子

人物在梯子格内不会下落。↑ 只能进入上方的梯子格；↓ 可以离开梯子向下走。在梯子格内左右移动遵守 4.2。梯子不支撑箱子。

### 4.4 挖取与背包

- 只能挖左、右、下三个相邻方向的夯土或沙。每挖一格背包 +1 袋，背包上限 9 袋。
- 背包只计"袋数"。1 袋 = 1 格 = 256 个 sand cell。
- 夯土【游戏层规则 + SDK static 材料】：褐色带碎石，不会坍塌，是主线中可挖墙体的主要材料。挖出来的同样是 1 袋沙。

### 4.5 倒沙

- 只能倒在左、右相邻、可进入且没有实体的格，每次倒 1 袋。SDK 中写入 256 个 sand cell，由求解器落下、堆积，沉入水中时把水挤上去。
- **设计约束**：主线中需要成为整格的倒沙，落点必须靠墙或落进坑里。空旷平地上的一格沙会摊成小坡，按阈值仍可能判为一格，但不作为解题关键。【待验证：靠墙一格沙的溢出量必须少于 128 cell。】

### 4.6 炸药（第 3 组起）

- 只能放在左、右、下三个相邻格。模型中会清除目标格及其上下左右四格内的裂岩、夯土和沙；基岩、箱子、门不受影响。
- SDK 中执行 `explode(格中心, 20, 8000)`。爆炸**没有遮挡**【SDK，已核实】：墙后面的格也会受影响，只按距离和抗爆性判断。剩余不足一半的裂岩格整格崩落（v0.3 做法）。
- 人物不受伤害。

### 4.7 压板与门【游戏层】

- 压板格被人物、箱子或任何实心材料压住时视为按下。同一关所有同符号的压板都按下，对应的门才打开。
- 门打开时清除门格材料；关闭时写回。门格内有人物或箱子时，门保持打开直到让开，不挤压、不吞物。
- 门和压板用同一形状符号配对（圆、三角、方块），不只靠颜色区分。第 1 组每关最多一组。
- 锁存门（离开后仍保持打开，并亮锁存灯）留到第 2 组以后，并且必须单独教学。
- **门是覆盖层**：开着的门格可以有水流过；门格里有人物、箱子、水或沙时，门保持打开（不挤压、不吞物、不删水）。
- **开关**【游戏层】（第 2 组起）：人物站在开关格按 ↑ 拨动一次，可以来回拨。开关要么控制一组门（`links` 中的一组；开关拨开时这组门一直开着），要么触发一个机关（升降台、释放口、火盆、喷口）。开关和它控制的门用同一个符号。

### 4.8 目标与过关

- 每关有一个或多个**目标灯**。所有目标灯同时点亮，即在该次结算结束时过关。
- 目标类型：箱子槽（槽内有箱子）、出口旗（人物站在旗上）、收集斗（斗内材料达到刻度，并锁存保持点亮，第 2 组起）。
- HUD 显示"已点亮 / 总数"。过关时播放约 1.2 秒的庆祝动画，按任意键可以跳过。

### 4.9 水（第 2 组起）【SDK + 游戏层】

- 水由 SDK 模拟。设计模型按整格近似：水往低处流；连通的水面最终拉平（两边只差不到一格时保持不动）；水面边上是空的落差时，水从边上流下去。
- **水量约束**：水永远装在井、渠、池、斗里，不在平地上摊开；一池水的格数要正好填满整数行。模型按整格算，SDK 会把多出来的水摊成薄层，两者就对不上。
- **人不在 SDK 里**：人在水里会沉到底，不挡水，也不被水推动；出水靠登一格或梯子。
- **箱子进水**【游戏层】：箱子进入有水的格时，游戏层先把这一格的水挪走，水不能凭空消失。铁箱下沉时和下面的水交换位置；推进、传送进水里时，这一格的水挪到同一片水的水面上（水面上没有空位时，这个动作无效）。
- **木箱上浮**【游戏层】：木箱上方一格是水时，木箱和这格水交换位置；木箱下面连着的那片水，最高水面比木箱底部高出 1.5 格以上时，木箱上浮一格，并从最高水面取一格水填进木箱腾出的格子。所以木箱总是浮在水面上一格，铁箱总是沉到底。
- 沙倒进水里会沉到底，把水挤上来（SDK 粉末与液体交换位置）。
- 【待验证】这些规则在 SDK 中的阈值和阶段长度，由开发方在第 2 组样板中实测（6.6）。

### 4.10 承重桥（第 2 组起）【游戏层】

- 桥板（图例 `=`）是平台：能站人、能放箱子，挡住水和沙。每座桥有承重 `capacity`。
- 每次结算后统计压在桥上的重量：站在桥板上的人和箱子，以及叠在它们上面的人、箱子和沙（人 1、木箱 1、铁箱 2、沙每格 1）。超过承重，整座桥塌下：桥板清除，上面的东西落下。
- 载重正好等于承重时，桥板显示裂纹；板面上的刻痕表示承重，压上的重量点亮，压满变红。
- 塌了的桥不会恢复（撤销可以）。
- 配送模式里同一机制画成地府的奈何桥、安第斯的草绳桥（[worlds.md](worlds.md)）。

### 4.11 传送阵（第 2 组起）【游戏层】

- 传送阵成对出现，用同一个符号配对（符号画在阵上方）。
- 每次结算静止后，停在一个阵上的人或箱子被送到另一个阵，前提是另一个阵空着（没有人、箱子和固体；有水可以，箱子传进水里按 4.9 挤开水）。
- 刚传过来的东西离开那个阵之前不会被传回；离开后再踩上去，才会再传。
- 只传人和箱子，不传水、沙等材料。
- 配送模式里的兔子洞、鸟居是同一机制换美术。

## 6 关卡模式

### 6.1 结构（关卡模式 v2，2026-10-15）

**用户要求**：第一批关卡最好把现有的 SDK 机制和不需要 SDK 的机制融合起来；评估之前定的地图是推倒重做还是保留。

**评估结论：保留，不推倒。** 六张地图（主题）、第 1 组 7 关和全部格子规则都留下；第 2–5 组从"一关一个 SDK 机制"改成"融合章"。

### 6.5 关卡规格格式与图例（全部模式通用）

每关一个文件 `content/levels/<模式>/<组>/<编号>.json`，格式 `pushbox.levelspec/1`，字段与第 1 组相同：`id`、`chapter`（主题键：`dungeon` / `ruins` / `cave` / `forest` / `sky` / `cosmos`）、`mode`（`lab` 关卡模式、`hell` 地狱模式）、`group`（关卡模式的组目录名）、`mechanisms`（本关演示的机制编号，对应机制目录）、`order`、`title`、`role`、`teaches`、`requires`、`discovery`、`map`、`bag`、`solution`、`hints`、`misreads`、`sdk`、`checks`。第 2 组起另有可选字段：`devices`（机关）、`links`（压板、开关与门的配对）、`water`（同时有水的格，见下）、`weather`、`profile`（启用的求解器）。关卡文字同时写进语言表（第 1、2 组在 `content/i18n/`，由美术负责人随界面一起确认；之后的组在 `content/i18n-extra/`），键为 `level.<编号>.title / discovery / hint.<n>`。

地图字符（每个字符 = 一格 = 16×16 cell）：

| 字符 | 含义 | 组 | 字符 | 含义 | 组 |
|---|---|---|---|---|---|
| `#` | 基岩 | 全部 | `g` | 碎石（慢速粉末） | 3 |
| `%` | 裂岩 | 3 起 | `f` | 引信 | 3 |
| `e` | 夯土 | 全部 | `a` | 酸液 | 4 |
| `s` | 散沙 | 全部 | `L` | 软岩（刻纹 A，可酸蚀） | 4 |
| `~` | 水 | 2 起 | `M` | 软岩（刻纹 A 的另一种外观，同标签） | 4 |
| `\|` | 门（关闭） | 全部 | `R` | 硬岩（不可酸蚀，用来对照） | 4 |
| `.` | 空 | 全部 | `^` | 轻烟（上浮气体） | 4 |
| `H` | 梯子 | 全部 | `v` | 沉雾（下沉气体） | 4 |
| `o` | 箱子槽 | 全部 | `w` | 木栅（可燃） | 5 |
| `X` | 出口旗 | 全部 | `i` | 冰（装置冰，无自然融化） | 5 |
| `_` | 压板 | 全部 | `P` / `h` | 人物 / 梯子上的人物 | 全部 |
| `B` / `I` | 木箱 / 铁箱 | 1 / 2 起 | `b` | 已在槽中的木箱 | 全部 |
| `p` | 菌塞（静止；被释放口换成带寿命的菌塞后按时消失） | 4 | `=` | 承重桥板（4.10，属于某个 `bridge` 机关） | 2 |

一格只能写一个字符。水下的压板在地图上写 `~`，坐标写进 `links.plates`；水下的梯子、目标槽、出口在地图上写标记字符，坐标写进 `water`（这些格同时有水）。木箱放在水面上一格（下面是 `~`）就是浮着的。

`links`：`[{"plates": [[x, y], ...], "doors": [[x, y], ...], "symbol": "circle" | "triangle" | "square", "latch": false}]`。不写时，全图所有压板控制所有门（第 1 组就是这样）。一组可以没有压板，只由开关控制（`lever` 的 `action: {"link": 组序号}`）。`symbol` 画在未踩下的压板和门上（`mech.link_symbol`），不写时按组序号依次取圆、三角、方。

`devices`（坐标都是格坐标）：

| 类型 | 字段 | 规则 |
|---|---|---|
| `lift` 升降台 | `stops: [[x, y], [x, y]]`（台面所在格，台面与该行地面平齐）、`button: [x, y]`（可选）、`width` | 人或箱子踩上按钮时触发一次，去另一站；也可以由开关或收集斗触发。站在台面上的东西一起走；载物受阻时拒绝移动；到站无限等待。台面所在格算支撑 |
| `bin` 收集斗 | `rect: [x, y, w, h]`、`material`、`need`（cell 数）、`latch`、`trigger`（可选） | 结算期间用 `count_materials` 计数。`latch: true` 时它是一盏目标灯，达标后锁存点亮；`trigger: {"device": 序号}` 时达标的那一刻触发那个机关一次 |
| `lever` 开关 | `at: [x, y]`、`action`（见下） | 人物站在开关格按 ↑ 拨动一次（可来回拨） |
| `portal` 传送阵 | `pads: [[x, y], [x, y]]`、`symbol`（可选） | 4.11 |
| `bridge` 承重桥 | `cells: [[x, y], ...]`（地图上写 `=`）、`capacity` | 4.10 |
| `torch` 火盆 | `at: [x, y]`（火盆所在格）、`area: [x, y, w, h]`、`temperature`、`phase_ticks` | 由开关触发：在作用区写一次温度圆，按固定阶段结算 |
| `frost_vent` / `heat_vent` 冷凝 / 热喷口 | `at`（喷口所在格）、`area`、`layer`、`value` | 由开关触发：写一次 layer，耦合器 `stride = 1` 当 tick 转换水与冰 |
| `vine` 藤梯 | `root: [x, y]`、`height`、`need`（根部水 cell 数） | 根部有水达标后，长出固定高度的梯子 |
| `release` 释放口 | `cells: [[x, y], ...]`、`to`（材料名） | 由开关或压板触发：把这些格换成指定材料（例如 `"plug_decay"` 带寿命的菌塞、`"empty"` 打开储水口） |

`action` 取值：`{"link": <links 组序号>}`（开关拨开时这组门一直开着）、`{"device": <设备序号>}`（触发升降台、火盆、喷口）或 `{"release": <设备序号>}`。

**外观以工作台为准**：这些材料、机关和特效的样子，以 `workbench/js/core/matter.js` 和工作台「场景」页的「第 2–5 章代表场景」为准（美术方向第 11 节）。代表场景里另有 `preview`（插图状态：开关已扳动、藤梯已长出、升降台停在哪一站）和 `fx`（摆好的特效）两个字段，只在工作台里用，关卡规格不要写。

### 6.6 关卡制作流程与难度预算（第 2 组起）

1. **先做该组的 SDK 样板**（每种机制一个最小场景，验证【待验证】项和阶段长度），通过后才画关卡。关卡模式的关卡本身就是很小的场景，样板验证通过后通常可以直接扩成关卡。
2. **按概念卡写规格**：每关只有一个新发现；作者解约 4–12 步，不超过 16 步；关卡不超过 20×10 格；不要求精确时机或抢时间；目标、开关和受控物尽量同屏；首次出现的机关要有安全的试错空间。
3. **在真实 SDK 中验证**：作者解通关，连续回放 3 次结果一致；每一步都能撤销；记录结算 tick 数，不得触顶。设计模型覆盖第 1 组和第 2 组的整格规则（水按整格近似，4.9），不能代替 SDK 验证；爆炸、反应和冷热的连锁不在模型里。
4. **交设计审核**：每组完成后，把规格、回放记录、截图和遇到的问题写进 `docs/status.md`，由设计负责人审核。审核前，这些关卡只在"开放全部关卡"设置下可玩。
5. **缺的美术用标明的占位**，列进待美术清单；正式美术由美术负责人制作、用户确认后再替换。
6. **更新机制目录**：每关的验证结果写进 Godot 的验证报告（[工作台](workbench.md) 第 4 节），工作台据此显示每个机制、每关的状态。

### 6.7 新机制加入流程（实验组）

以后给 SDK 或游戏层加新机制，一律走这个流程，不直接用进配送模式或地狱模式：

1. **登记**：在 `content/catalog/mechanisms.json` 加一条，状态 `proposed`，写明归属（SDK / 游戏层）、需要的 SDK 能力、风险。
2. **SDK 改动**（如需要）：按 SDK 仓库自己的流程修改和发布。
3. **最小关卡**：在实验组写一关，只演示这一个机制，验收条目必须能在 Godot headless 中自动运行。
4. **验证**：真实 SDK 回放 3 次结果一致、撤销完整、结算不触顶；结果进验证报告，状态改为 `verified`。
5. **美术**：缺的资产先用标明的占位，再由美术负责人制作、用户确认。
6. **开放**：状态改为 `playable`；设计负责人决定它留在实验组，还是移入某个正式组。之后它才可以用于配送模式和地狱模式。

改动 SDK 后，关卡模式的全部关卡都要重新跑一遍验收，作为回归测试。

## 7 系统

### 7.1 撤销与重开

- 每个合法动作前保存撤销点：SDK `save_snapshot` 写入 `user://undo/`，同时保存游戏层状态 JSON（实体、背包、门、目标锁存、装置）。上限 200 步。
- 撤销恢复快照和游戏层状态，不重放；重开读取开局快照。重开本身也算一个撤销点。
- 关卡退出时清理快照目录。
- 实验组若使用刚体：带刚体的快照读回后不保证位级一致【SDK，已核实】，只能改为"从无刚体的开局重放全部命令"实现撤销，届时单独设计。

### 7.2 提示

1. 第一层：高亮相关对象（关卡数据 `hints[0]` 的文字，加上对象描边）。
2. 第二层：说明因果关系（`hints[1]`）。
3. 第三层：说明下一步怎么做（`hints[2]`），并提供"演示"按钮。演示从当前状态播放作者解的剩余步骤；当前状态不在作者路线上时，按钮改为"回到最近的正确位置"——从撤销历史中找出最近一个与作者路线某步一致的状态并撤销过去；找不到时提示重开。
- 状态一致性只比较游戏层局面（人物、箱子、格子分类、背包），不比较 SDK 哈希（哈希包含 tick 数，不适合用来比较）。
- 使用提示不影响通关、解锁和任何记录。

### 7.3 跳关

关卡选择界面允许直接进入任何已解锁的关卡。暂停菜单提供"跳过此关"：标记为已跳过（不算通关），回到关卡选择。规则卡机制见 6.2。

### 7.4 观察与目标高亮

- **观察**（按住 Tab）：显示格子网格、格子分类小图标、压板与门的配对连线、目标灯列表；画面变暗 30%，人物不可操作。
- **目标高亮**（悬停或按住修饰键时）：只显示按规则确定的结果，不运行模拟。包括挖取目标格、倒沙落点所在的整列、炸药的十字影响区（标出会崩落的格）、推箱后的箱子落点。
- **取消 v0.3 的整局预演模拟**：它需要第二个 SDK 世界和分帧调度，复杂度高；撤销已经免费，因此不再保留。

### 7.5 存档

`user://progress.json`，带 `version` 字段：

```json
{"version":1,"levels":{"M01":{"cleared":true,"skipped":false,"best_steps":4}},
 "chapters_unlocked":["mine"],"rule_cards_seen":["push"],
 "settings":{"open_all_levels":false,"ambience":"full","language":"zh-Hans","show_grid":false,"music":0.8,"sfx":0.8,"window_scale":"auto"}}
```

写入采用"先写临时文件，再改名"。读取失败时备份损坏文件并重建。

### 7.6 引导

教学关的动作提示做对一次后就消失，并记录在 `rule_cards_seen` 中；设置里提供"重看引导"。键位提示使用按键图标（见美术清单 `ui.key.*`）。

**环境效果**：每个主题有自己的光照与可选天气（见美术规范第 9 节），纯视觉，不影响规则；设置中的「环境效果」可选全部、只要光照或关闭，也是低配机器的性能开关。关卡规格可用 `weather` 字段指定一种天气。

界面文字使用 Fusion Pixel 12px（覆盖简中、拉丁扩展、日文假名、韩文、西里尔字母），最近邻渲染，关闭抗锯齿。界面不出现 tick、cell 数量、温度数值等技术参数。

**多语言**：首发简体中文与英文，界面设计按任意语言排版（规则见美术规范第 7 节）：

- 所有界面文字来自 `content/i18n/<语言>.json`，用 `{name}` 占位，不拼接句子；新增语言只加一个文件。
- 容器按测得的文字宽度伸缩（菜单、按钮、提示面板），有最小与最大宽度；仍放不下的文字换行或省略，并在开发构建中报出。
- 章节卡、关卡行、HUD 用数字、图标和主题徽章表达信息，完整文字放在宽度充足的说明栏里。
- 中文按字断行，标点不出现在行首；英文等按词断行。
- 设置中可以切换语言，切换后立即生效。

## 9 实验组候选（不在当前范围）

以下机制等关卡模式前 5 组完成并经过试玩后再决定，每项都按 6.7 的流程进入实验组：

## 10 验证分层

| 层 | 证明什么 | 由谁执行 | 不能替代 |
|---|---|---|---|
| 设计审阅 | 职责清楚、前置知识齐全、难度预算合理 | 设计负责人 | 有解性 |
