# 关卡质量标准（关卡补强用）

状态：**有效**（2026-10-16，用户安排"关卡补强现在排"）。适用于关卡模式全部章节，第 3–6 章的补强按本文件做；与 [game-design.md](game-design.md) 6.1、6.6 一起用（那里的步数预算、"一关一件新事"仍然有效，本文件把"好关卡"写成可检查的条件）。

## 1 为什么要补强

开发方（GPT）先补齐了第 3–6 章 30 关规格（`codex/portitor-stage1`），审核结论：普遍 4–7 步、一条路走到底，更像"这个机关的演示"，没有让玩家想一下的地方；第 6 章只是两个旧机关拼接；设计模型不认识第 3–5 章大部分机关，20 关没有可信的检查结果（[status.md](../status.md) 的审核一节）。

## 2 一关要满足的条件

1. **一个发现**：玩家第一次看到时，直觉的做法是错的或不够，想通"机关真正怎么作用"之后才过关。写进规格的 `discovery` 字段，一句话说清"想通了什么"。
2. **一个诱饵或一个先后**：至少有一个看起来能行、其实不行的做法（诱饵），或者两件事必须按正确的先后做。不能是"一条走廊，按顺序把东西都碰一遍"。
3. **看得见的因果**：开局就能看见机关、目标和受控物（尽量同屏）；失败时一眼能看出为什么（死局可以有，撤销或重来后要明白原因）。
4. **步数**：章内前 1–2 关（引入关）6–10 步；其余 8–14 步；章末组合关 10–16 步；不超过 16 步（game-design.md 6.6）。不要求精确时机。
5. **没有捷径**：设计模型找到的最短解不能比作者解短 2 步以上；短了就是有没想到的捷径，要堵住或者改成作者解。
6. **能检查**：作者解在设计模型里通过；非引入关的死局状态数大于 0（有走错的可能）。模型还表达不了的效果（爆炸、反应、冷热的连锁），在规格的 `checks` 里写清楚要在 SDK 里核对什么。
   - `checks` 只写 SDK / 游戏回放能判定通过或失败的条目。"模型边界"说明和"待用户美术确认"写进 `notes`，不进 `checks`（否则这一关永远算不上 SDK 验证通过）。
   - 写进 `checks` 的数量要写成判据（例如"右根水量 < 256、藤不长"），不要把还没测过的细胞级分布写成承诺。
   - SDK 材料的摆法照 [game-design.md](game-design.md) 第 4 组"酸的摆法"、4.1"箱子进入有薄层粉末的格"、第 3 组的引信阶段和碎石速度；收集斗（沙、碎石、水）的两侧和底要封闭，不能开在人走的走廊里；粉末从高处落进斗时，经过开着的格会有少量（实测每侧约 6 cell）滑开，`need` 不要写成正好装满（Q04 用 512 中的 448）。粉末要停在某个位置（例如箱顶）时，那一格两侧也要封住。
   - 提示文字：英文一条提示控制在约 120 个字符以内，才放得进四行气泡（LV-10 实测 164、177 个字符溢出）。
7. **一关一件新事**：引入关只教一个机关；组合关只组合"已经学过的"两件事，并且组合本身是新的发现（不是两件事各做一遍）。

## 3 一章的结构

- 前 1–2 关是引入关：安全地看懂机关（可以没有死局，但仍要有发现）。
- 中间几关：同一机关的变化（反着用、和地形配合、和已学的推 / 挖 / 倒配合）。
- 章末 1 关：轻组合（本章两件事，或本章 + 前面章节一件事），是本章最难的一关。
- 难度单调上升；相邻两关不要教同一个发现。

## 4 第 6 章（实验）

`groups.json` 里第 6 章原本留给以后的新 SDK 机制。开发方先放了 E01–E06 作为"两个旧机关的组合"。补强时把第 6 章定位为**跨章组合复习**：每关组合两个来自不同章节的机关，组合必须产生新的发现（例如"冻出冰道，让矿车滑过去"），不是两件事各做一遍。以后真有新 SDK 机制时，再按 game-design.md 6.7 加进实验组。

**用户决定（2026-10-16）**：关卡模式暂时只用现有的 33 个机制（第 1–5 章已排进关卡的）。SDK 已有、但还没有关卡的 4 项能力——电与机关 `power`、沙炮 `particles`、落石 `rigid`、风道 `pressure`——以及各地区的新机制，**等现在这些关卡在 Godot / SDK 里跑通之后**，再开新章节来做。

## 5 审核时看什么

设计负责人审核补强后的关卡时只看：本文件第 2 节的 7 条是否满足（模型检查结果、步数、`discovery`、诱饵或先后写在规格的 `idea` / `notes` 里）、章的结构是否符合第 3 节。手感和真实物理以 Godot / SDK 验证为准。
