# 外包工作流程

用户 2026-10-17 决定：以后所有工作，包括设计，都拆成**工作包**外包给其他 AI 做。Claude 只做最后的**整理合并**。本文件是这种工作方式的规则，所有协作者都要遵守；AGENTS.md 第 0 条指向这里。

这些规则来自已经出过的问题：
- 两边都新建了 `UI-07`；
- 测试还按旧菜单检查；
- 远端分支没更新，内容只在 bundle 里；
- 生成文件冲突；
- 改了参与哈希的文件，导致美术换版本；
- 一包改了别的包要改的文件。

## 1 角色

| 谁 | 做什么 | 不做什么 |
|---|---|---|
| **用户** | 把包派给制作方；确认美术（只有用户能确认）；在包写明的问题上拍板 | — |
| **制作方**（任何 AI，包括另开的 Claude 窗口） | 按一个包做完，跑完包里的验收命令，填「交付」，按第 4 节交回 | 不做包外的事；不改 `docs/status.md`；不合并进 `main`；不删分支 |
| **设计方**（接设计包的制作方） | 写设计文档和设计目录 `content/catalog/**`，把功能拆成新的工作包 | 不写代码、不画美术、不做房间 / 关卡数据 |
| **Claude（整理合并）** | 导入交回的分支或 bundle；按第 7 节核对；合进 `main`；处理冲突；重新生成；更新 `docs/status.md`；排下一批；分支清理 | 不重做制作方的工作；不通过就写明原因，列进下一批 |

## 2 工作包

- **一包一个文件**：`docs/packages/<编号>.md`，格式见 [packages/README.md](packages/README.md) 的模板。
- **一包一次会话能做完**；做不完就拆。
- **包头要写**：
  - 编号、状态；
  - **基线**：从哪个分支开，默认 `main`；
  - **分支名**；
  - **可改的文件**（清单之外一律不改）；
  - **会碰的共享文件**（第 5 节）；
  - **允许换版本的美术**（没写就是 0 个）；
  - 验收命令和预期结果。
- **状态**：
  - 待做 → 进行中（制作方开工时改）→ 已交回（制作方交付时改）→ 已合并 / 退回（Claude 改）。
  - 退回时写明原因和下一步。

### 2.1 包要小（2026-10-17，DSN-01 复盘后加）

DSN-01 一个包里有设计、22 项美术、地形代码、目录、两个新包，会话被自动压缩了好几次；压缩后制作方忘了做过什么，就重复核对、返工，也容易"记错"。所以：
- **一个包只做一类事**：设计、美术、代码、数据，各自分包。
- **一个包预计 2–3 小时做完**，最多不超过 4 小时；新文件大约 10 个以内。美术一包不超过 8 项。
- 预计超时的，Claude 派包前就拆开，按顺序编号（例如 ART-01a、ART-01b）。

## 3 编号

- **编号只在 [packages/README.md](packages/README.md) 的「编号登记」表里分配**。新包先登记，再写文件。
- **前缀**：

| 前缀 | 内容 |
|---|---|
| `DSN` | 设计 |
| `LV` | 关卡 |
| `UI` | 界面 |
| `DLV` | 配送 |
| `ART` | 美术 |
| `WB` | 工作台 |
| `UX` | 体验 / 调研 |
| `AUD` | 声音（音效、音乐） |
| `BR` | 分支整理 |

- **设计包会拆出新包**：派出前由 Claude 在登记表里给它**预留编号**，写在包里。不够用时用 `<父包号>-x1`、`<父包号>-x2` 临时编号，Claude 合并时再改成正式编号。
- **制作方不能自己取新编号**。

## 4 分支与交回

- **开分支**：从包里写的基线开，分支名 `<前缀小写>/<编号>`，例如 `dlv/DLV-03`、`dsn/DSN-01`。
  - **基线以包头写的为准**。BR-01 做完之前，`main` 还是旧内容，基线一律是 `claude/inspiring-ride-zfnn4s`；之后改为 `main`。
  - 每个包的包头都写好了开工和交回的命令，照抄即可。
  ```bash
  git fetch origin
  git checkout -b <分支> origin/<基线>
  ```
- **只提交这一包的改动**：
  - 不 rebase、不 amend、不强推；
  - 不合并别的包的分支；
  - 不往 `main` 和基线分支上推。
- **交回**（二选一）：
  - 能推送：`git push -u origin <分支>`；
  - 不能推送：`git bundle create <编号>.bundle origin/<基线>..<分支>`，把文件交给用户。
- **包的「交付」一节必须写**：
  - 分支名和最后一个提交号；
  - 验收命令的实际输出（贴结果行即可）；
  - `git diff --stat origin/<基线>..<分支>`；
  - 没做完的地方和「问题」。
- **一个包只交一次**；退回修改时在同一分支上继续提交，再交一次。

## 5 共享文件（"热点"）

这些文件很多包都会碰，最容易冲突。

| 文件 | 规则 |
|---|---|
| `workbench/index.html` 的脚本列表、`tools/art.mjs` 的 `loadCore` 列表、`tests/i18n.test.mjs` 的字体列表 | 只在末尾或相邻位置**追加**，不删、不重排 |
| `workbench/js/app/nav.js` 菜单 | 只加自己的项；改已有项要在包里写明 |
| `content/catalog/*.json` | 只有设计包能改；只加或改包里写明的条目，不重排 |
| `docs/packages/README.md` | 只改登记表里本包的行；设计包可以加预留编号的行 |
| `docs/status.md` | 只有 Claude 改 |
| 生成文件：`art/export/**`、`workbench/data/*.js`、`content/export/*.json`、`content/*.generated.json`、`game/generated/**` | 可以提交重新生成的结果，但**不手改**；冲突时 Claude 任取一边后重新生成 |

**同一批派出的包不能改同一个非追加的共享文件**。Claude 排批次时检查；包里「会碰的共享文件」要写全。

## 6 检查：边做边跑小的，最后跑一次全套（2026-10-17 改）

以前要求"全套命令都要跑"，结果制作方每改一点就跑全套。DSN-01 跑了 15–25 次美术构建，单测加浏览器测试一轮就要 3 分钟。现在分两档：

1. **做的过程中**：只跑包里「边做边跑」列的那一两条快命令（通常是 `content.mjs check` 和本包相关的一条）。
   - 画美术时先用自己的预览脚本看图，满意了再 `art.mjs build`，不要每改一笔就 build。
2. **交回前跑一次全套**，包里「最后跑一次」列的命令，**只跑一遍**；失败了修好再跑失败的那条，以及受影响的几条。常见的全套：
   - `node tools/content.mjs check` → 0 错误
   - 本包相关的检查工具（`check-levels`、`check-rooms2`、`audio.mjs verify` 等，包里写明）
   - `node tools/art.mjs build` → 换版本的只能是包里允许的资产（默认 **0 bumped**），确认记录条数不变
   - `node --test tests/*.test.mjs`
   - `node tests/workbench.e2e.cjs`：只有改了网页或生成文件时才跑
   - 只改文档的包：只跑 `content.mjs check`。
3. **新资产就是第 1 版**；改已有资产，最后的版本号 = 基线上的版本 + 1。中间多次 build 不会把版本号推高，不用反复确认。
4. **改了菜单、文字、页面结构，要同时改测试里的预期**，并在交付里写明改了哪条测试、为什么。不许删测试或放宽断言来求通过。
5. **改动范围自查**：`git diff --stat` 看一眼，每个文件都在包的「可改的文件」清单里即可。**不要**逐个算文件哈希来证明没改别的。
6. **冻结区**（AGENTS.md 2a）：没写允许就不碰。看到意外的美术换版本，就是改错了文件。

## 7 Claude 合并前核对清单

1. 导入：`git bundle verify`，或 `git fetch` 远端分支。核对分支名、提交号和交付里写的一致。
2. **范围**：`git diff --stat` 对照包的「可改的文件」；超出范围的改动退回，或者只取范围内的部分。
3. **编号**：新包编号对照登记表；冲突就改临时编号（第 3 节）。
4. **规则**：
   - 冻结区没动；
   - 美术换版本只在允许清单内；
   - 没有自行批准美术；
   - 没改 `docs/status.md`。
5. 合进 `main`（普通合并），共享文件按第 5 节解决，重新生成生成文件，跑第 6 节全套检查。
6. 更新 `docs/status.md` 和包状态；有问题写明原因，列进下一批。推送后告诉用户结果和下一步要派的包。

- 每次合并或派包后，更新进度看板 `docs/board.md`（给用户看的一页纸：在做 / 可以派 / 在等 / 搁置 / 等用户做的事）。

## 7a Claude 派包前自检（2026-10-17，DSN-01 复盘后加）

DSN-01 的返工大多是包本身的毛病：验收要求做到的事，要改的文件却不在「可改」清单里；数据该放哪没说清。派包前 Claude 逐条过一遍：
1. **验收和可改清单对得上**：每条验收要做到的事，需要改的文件都在「可改」清单里；做不到的验收条目删掉，或者把文件加进清单。
2. **数据放哪写清楚**：新条目放进哪个文件、哪一段（例如 `slices.json` 的 `planned` 还是 `entries`），会不会让现有检查报错。
3. **已知的坑写进包**：版本号怎么算、哪些已确认资产不能改（要另做新资产）、尺寸等默认值。
4. **大小**：按 2.1 节检查，超了就拆。
5. **冲突时谁优先**：包里写一句"验收和可改清单冲突时，以可改清单为准，把做不到的写进交付，不要想办法绕过"。

## 8 标准提示词

派包时给制作方的提示词用下面这一段，只换三处：`<分支>`、`<基线>`、`<编号>`（包头都写着）。**先切分支再读包**，否则读不到新写的包。

```
你在仓库 beekim123/ele-pushbox 工作（像素解谜游戏《渡界人 · PORTITOR》）。

第一步，先切到正确的分支：
git fetch origin
git checkout -b <分支> origin/<基线>

然后读 AGENTS.md，以及 docs/process.md 的第 4、6、10 节（其他节是给合并方的，不用读）；再读 docs/packages/<编号>.md，只做这一个包。
所有提交只放在 <分支> 上，不往 <基线>、main 或别的分支推送，也不合并别的分支。

严格按包里写的做：只读包里列的文件，边做边跑包里列的快命令，最后只跑一次全套检查；不要做包里没要求的验证（见 process.md 第 10 节）。
结果写进包的「交付」，不超过 40 行。预计时长写在包头；超时就停下，把进度写进「交付」交回。
会话很长时，在仓库外记一个简短的进度笔记，被压缩后照笔记继续，不要从头重新核对。
拿不准的事写进「交付 · 问题」，不要自己改设计。

交回（二选一）：
- 能推送：git push -u origin <分支>
- 不能推送：git bundle create <编号>.bundle origin/<基线>..<分支>，把 <编号>.bundle 交给用户

做完用中文简短告诉用户：做了什么、检查结果、交回方式（分支名或 bundle 文件名）、遗留问题。
```

如果派包时还得给提示词另外加话，说明包写得不够好，应该先改包。

## 9 文档要写清楚（用户 2026-10-17 要求）

工作包、设计文档、提示词都按这个标准写。写完自查：**一个第一次进这个仓库的 AI，只看这份文档，能不能不问任何问题就做对？**

- **不省略、不写"同上""照旧"**：基线分支、新分支名、开工命令、交回命令，每个包的包头都写全，命令可以直接复制。
- **不写模糊的默认值**：不写"默认 main"这种可能过时的话；要写，就写现在实际是哪个，什么时候会变。
- **不能做的事写成明确的清单**：写到具体的文件和分支，例如"不往 `main` 推送"、"不改 `terrain-diyu.js`"，并写出原因。
- **验收要可检查**：每条都是"运行什么命令 → 应该看到什么"，或者"打开哪一页 → 应该看到什么"。
- **给用户看的部分说人话**：用户不是程序员。先说结论和要用户做的事，技术细节放后面。

## 10 少做无用功（2026-10-17，DSN-01 复盘后加）

**不要做的事**（除非包里明确要求）：
- 逐个计算文件哈希、复制整个仓库做试验、在临时仓库里试导入 bundle；
- 逐帧比对动画、逐条比对目录：验收写"能看到、能播放"，就只检查这一点；
- 为写交付说明而补跑命令、重新核对已经确认过的事；
- 把 `git diff --stat` 写进仓库里的文件（文件本身会改变统计）。差异统计贴在给用户的回复里。
- 读和本包无关的文件：例如别的包、合并方用的 process.md 第 7 节。

**一个包一个工作目录**（2026-10-17，UI-10b / UI-10c / DLV-04b 同时做时互相混进了没提交的文件，检查结果被污染）：同时做几个包时，每个包用自己的目录，例如 `git worktree add ../ele-pushbox-<编号> -b <分支> origin/<基线>`，不要几个窗口共用一个仓库目录切分支。

**新字体文件要进字体清单**（2026-10-17，UX-02）：用 `build-font.py --ext <名>` 生成新的 `font-<名>.js` 时，同一个包里要在 `tools/art.mjs` 的 `loadCore` 列表、`tests/i18n.test.mjs` 的字体列表、`workbench/index.html` 的脚本列表各追加一项，否则缺字测试会失败。写包时把这三处放进「可改的文件」。

**测试报告只提交完整跑完的**（2026-10-17，UI-06a）：`game/reports/verification.json` 记着 30 关的 SDK 结果，`content.mjs` 用它算机制和关卡状态。默认全套没完整跑完时不要提交它（`git checkout -- game/reports/verification.json`），否则会把已有记录清空。

**会话很长时**：在仓库外记一个简短的进度笔记，写做完了哪几步、做了哪些决定。会话被自动压缩后，照笔记继续，不要从头重新核对。

**交付说明**：照包里模板的几条写，**不超过 40 行**。不要照以前包的长篇交付写。

**环境小抄**：
- 测试浏览器找不到：
  - Mac：`PLAYWRIGHT_MODULE=/Users/key_/.cache/codex-runtimes/codex-primary-runtime/dependencies/node/node_modules/playwright`，`PLAYWRIGHT_CHROMIUM_EXECUTABLE='/Users/key_/Library/Caches/ms-playwright/chromium-1217/chrome-mac-arm64/Google Chrome for Testing.app/Contents/MacOS/Google Chrome for Testing'`
  - Linux 沙箱：`PLAYWRIGHT_CHROMIUM_EXECUTABLE=/usr/local/bin/chromium`
- 路径里有软链接时用绝对路径改文件；长文件分段写，不要用一个很长的 here-document。
