# 外包工作流程

用户 2026-10-17 决定：以后所有工作，包括设计，都拆成**工作包**外包给其他 AI 做。Claude 只做最后的**整理合并**。本文件是这种工作方式的规则，所有协作者都要遵守；AGENTS.md 第 0 条指向这里。

这些规则来自已经出过的问题：
- 两边都新建了 `UI-07`；
- 测试还按旧菜单检查；
- 远端分支没更新，内容只在 bundle 里；
- 生成文件冲突；
- 改了参与哈希的文件，导致美术换版本；
- 一包改了别的包要改的文件。

## 1 角色

| 谁 | 做什么 | 不做什么 |
|---|---|---|
| **用户** | 把包派给制作方；确认美术（只有用户能确认）；在包写明的问题上拍板 | — |
| **制作方**（任何 AI，包括另开的 Claude 窗口） | 按一个包做完，跑完包里的验收命令，填「交付」，按第 4 节交回 | 不做包外的事；不改 `docs/status.md`；不合并进 `main`；不删分支 |
| **设计方**（接设计包的制作方） | 写设计文档和设计目录 `content/catalog/**`，把功能拆成新的工作包 | 不写代码、不画美术、不做房间 / 关卡数据 |
| **Claude（整理合并）** | 导入交回的分支或 bundle；按第 7 节核对；合进 `main`；处理冲突；重新生成；更新 `docs/status.md`；排下一批；分支清理 | 不重做制作方的工作；不通过就写明原因，列进下一批 |

## 2 工作包

- **一包一个文件**：`docs/packages/<编号>.md`，格式见 [packages/README.md](packages/README.md) 的模板。
- **一包一次会话能做完**；做不完就拆。
- **包头要写**：
  - 编号、状态；
  - **基线**：从哪个分支开，默认 `main`；
  - **分支名**；
  - **可改的文件**（清单之外一律不改）；
  - **会碰的共享文件**（第 5 节）；
  - **允许换版本的美术**（没写就是 0 个）；
  - 验收命令和预期结果。
- **状态**：
  - 待做 → 进行中（制作方开工时改）→ 已交回（制作方交付时改）→ 已合并 / 退回（Claude 改）。
  - 退回时写明原因和下一步。

## 3 编号

- **编号只在 [packages/README.md](packages/README.md) 的「编号登记」表里分配**。新包先登记，再写文件。
- **前缀**：

| 前缀 | 内容 |
|---|---|
| `DSN` | 设计 |
| `LV` | 关卡 |
| `UI` | 界面 |
| `DLV` | 配送 |
| `ART` | 美术 |
| `WB` | 工作台 |
| `UX` | 体验 / 调研 |
| `BR` | 分支整理 |

- **设计包会拆出新包**：派出前由 Claude 在登记表里给它**预留编号**，写在包里。不够用时用 `<父包号>-x1`、`<父包号>-x2` 临时编号，Claude 合并时再改成正式编号。
- **制作方不能自己取新编号**。

## 4 分支与交回

- **开分支**：从包里写的基线开，分支名 `<前缀小写>/<编号>`，例如 `dlv/DLV-03`、`dsn/DSN-01`。
  - **基线以包头写的为准**。BR-01 做完之前，`main` 还是旧内容，基线一律是 `claude/inspiring-ride-zfnn4s`；之后改为 `main`。
  - 每个包的包头都写好了开工和交回的命令，照抄即可。
  ```bash
  git fetch origin
  git checkout -b <分支> origin/<基线>
  ```
- **只提交这一包的改动**：
  - 不 rebase、不 amend、不强推；
  - 不合并别的包的分支；
  - 不往 `main` 和基线分支上推。
- **交回**（二选一）：
  - 能推送：`git push -u origin <分支>`；
  - 不能推送：`git bundle create <编号>.bundle origin/<基线>..<分支>`，把文件交给用户。
- **包的「交付」一节必须写**：
  - 分支名和最后一个提交号；
  - 验收命令的实际输出（贴结果行即可）；
  - `git diff --stat origin/<基线>..<分支>`；
  - 没做完的地方和「问题」。
- **一个包只交一次**；退回修改时在同一分支上继续提交，再交一次。

## 5 共享文件（"热点"）

这些文件很多包都会碰，最容易冲突。

| 文件 | 规则 |
|---|---|
| `workbench/index.html` 的脚本列表、`tools/art.mjs` 的 `loadCore` 列表、`tests/i18n.test.mjs` 的字体列表 | 只在末尾或相邻位置**追加**，不删、不重排 |
| `workbench/js/app/nav.js` 菜单 | 只加自己的项；改已有项要在包里写明 |
| `content/catalog/*.json` | 只有设计包能改；只加或改包里写明的条目，不重排 |
| `docs/packages/README.md` | 只改登记表里本包的行；设计包可以加预留编号的行 |
| `docs/status.md` | 只有 Claude 改 |
| 生成文件：`art/export/**`、`workbench/data/*.js`、`content/export/*.json`、`content/*.generated.json`、`game/generated/**` | 可以提交重新生成的结果，但**不手改**；冲突时 Claude 任取一边后重新生成 |

**同一批派出的包不能改同一个非追加的共享文件**。Claude 排批次时检查；包里「会碰的共享文件」要写全。

## 6 必须做到的检查（制作方交回前）

1. **全套命令都要跑**，不只跑和自己相关的：
   - `node tools/content.mjs check` → 0 错误
   - `node tools/check-levels.mjs`、`node tools/check-rooms.mjs`、`node tools/check-rooms2.mjs` → 通过
   - `node tools/art.mjs build` → 换版本的只能是包里允许的资产（默认 **0 bumped**），确认记录条数不变
   - `node tools/art.mjs verify` → ok
   - `node --test tests/*.test.mjs`、`node tests/workbench.e2e.cjs` → 全部通过
2. **美术版本只升一次**：中间多次 build 产生的版本号不提交。最后的版本号 = 基线上的版本 + 1。
3. **改了菜单、文字、页面结构，要同时改测试里的预期**，并在交付里写明改了哪条测试、为什么。不许删测试或放宽断言来求通过。
4. **改动范围自查**：`git diff --stat` 里每个文件都要在包的「可改的文件」清单里。
5. **冻结区**（AGENTS.md 2a）：没写允许就不碰。参与美术哈希的文件改了，build 会显示换版本；看到意外的换版本就是改错了文件。

## 7 Claude 合并前核对清单

1. 导入：`git bundle verify`，或 `git fetch` 远端分支。核对分支名、提交号和交付里写的一致。
2. **范围**：`git diff --stat` 对照包的「可改的文件」；超出范围的改动退回，或者只取范围内的部分。
3. **编号**：新包编号对照登记表；冲突就改临时编号（第 3 节）。
4. **规则**：
   - 冻结区没动；
   - 美术换版本只在允许清单内；
   - 没有自行批准美术；
   - 没改 `docs/status.md`。
5. 合进 `main`（普通合并），共享文件按第 5 节解决，重新生成生成文件，跑第 6 节全套检查。
6. 更新 `docs/status.md` 和包状态；有问题写明原因，列进下一批。推送后告诉用户结果和下一步要派的包。

## 8 标准提示词

派包时给制作方的提示词只要这一段，具体内容都写在包里：

```
你在仓库 beekim123/ele-pushbox 工作（像素解谜游戏《渡界人 · PORTITOR》）。
先读 AGENTS.md 和 docs/process.md，严格遵守；然后读 docs/packages/<编号>.md，只做这一个包。
按 process.md 第 4 节开分支、交回，按第 6 节跑全套检查，结果写进包的「交付」。
拿不准的事写进「交付 · 问题」，不要自己改设计。
做完用中文简短告诉用户：做了什么、检查结果、交回方式（分支名或 bundle 文件名）、遗留问题。
```

包里没写清楚、提示词需要加话的情况，说明包写得不够好，应该先改包。
